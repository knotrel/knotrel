# Knotrel v1.1.0 Release Notes — Cluster Forest Backend

**Status: released 2026-11-25.** Adds the opt-in, experimental
`cluster-forest` engine; `compact-bfs` stays the default. Performance
qualification of the CF5 results for build `02cba68` accepted with
exceptions; their transfer to the 1.1.0 build is a separate maintainer
decision (see [Performance qualification](#performance-qualification)). Host
swap activity was not verifiable during the campaign.

## Scope

v1.1.0 adds a fourth connectivity engine, `cluster-forest`, **opt-in and
experimental**. `compact-bfs` stays the default engine. The 1.x contract of
v1.0.0 is unchanged: the new engine is a stable interface with an
experimental engine, like `ett` and `hdt`
([compatibility](../compatibility.md#22-stable-interface-experimental-engine)).
Lockstep: `knotrel-core`, `knotrel-server` and the console share the version
1.1.0 and one tag, `v1.1.0`.

**Start here: [Choosing an engine](../choosing-an-engine.md)**, the canonical
guide. It explains how `cluster-forest` works, when to try it and when to keep
`compact-bfs`, ETT or HDT, what the library and the server offer, with verified
examples and how to go back to `compact-bfs`.

## What is new since v1.0.0

**Cluster forest engine (CF1–CF4, [#150](https://github.com/knotrel/knotrel/pull/150)).**
- `EngineConfig::ClusterForest` (selector `cluster-forest`): a sequential
  cluster forest after Wulff-Nilsen (SODA 2013, §3) with the path compression
  of De Man et al. (PVLDB 2025, §4)
  ([ADR 0014](../architecture/0014-cluster-forest-backend.md)). Queries walk
  to the roots in `O(log N)`; updates are `O(log² N)` amortized by this
  project's derivation for this variant, not by a published theorem. At most
  2²⁸ vertices and 2²⁸ edges.
- Supported by `LifecycleGraph`: node activation, edge enabling and node
  removal, with enforced limits of 2²⁷ − 512 nodes and 2²⁸ edges.
- Server: `KNOTREL_ENGINE=cluster-forest`, with or without
  `KNOTREL_TOPOLOGY_LIFECYCLE=true`; `GET /v1/info` reports
  `"engine": "cluster-forest"` and `"experimental": true`. Incident and edge
  inspection needs lifecycle support with this engine. OpenAPI, HTTP API,
  stability and console types updated.
- Correctness (CF3): differential tests against `ReferenceGraph` and
  `compact-bfs`, seeded property histories with the full invariant checker,
  adversarial families and lifecycle churn across compactions.
- The PostgreSQL feeder's load tool selects the server engine with
  `LOAD_ENGINE` (`compact-bfs` or `cluster-forest`)
  ([#152](https://github.com/knotrel/knotrel/pull/152)).

## Compatibility

No breaking change: v1.1.0 follows the 1.x contract of v1.0.0
([compatibility policy](../compatibility.md)). The additions are the
`EngineConfig::ClusterForest` variant, the `cluster-forest` value of
`KNOTREL_ENGINE` and of `engine` in `GET /v1/info`, and the matching OpenAPI
and console types. The default engine and every existing selector behave as in
v1.0.0. Lockstep: `knotrel-core`, `knotrel-server` and the console are 1.1.0.

The console's browser tests (Chromium and Firefox; `npm run build`, then

Console 1.0 keeps its declared support for server 0.9.

## Performance qualification

**Qualification of the CF5 results for build `02cba68`: accepted with
exceptions** (knotrel-benchmarks
[`results/v1.1.0-cf5/DECISION.md`](https://github.com/knotrel/knotrel-benchmarks/blob/main/results/v1.1.0-cf5/DECISION.md),
the decision record). The CF5 campaign
([plan](v1.1.0-cf5-qualification-plan.md),
[report](https://github.com/knotrel/knotrel-benchmarks/blob/main/results/v1.1.0-cf5/REPORT.md))
ran on build `02cba68` (crate version 1.0.0 on `main`), on one Apple M3 host,
on 2026-11-24 and 2026-11-25. It did two things:

- **Regression checks of the existing engines against v1.0.0** (V1, V2),
  published as the
  [1.1.0 release page](https://knotrel.github.io/knotrel-benchmarks/releases/1.1.0.html):
  no regression and no failure; five checks are left open with their classes
  (two UNRESOLVED and one INCONCLUSIVE_DISCLOSED on HTTP cells with
  `compact-bfs`, two TIMER_LIMITED on `ett`). None is a regression or a pass.
  Summary for users: [performance by version](../performance-by-version.md).
- **`cluster-forest` against `compact-bfs`, ETT and HDT on the same build**,
  an engine comparison, not a release comparison: results by workload family
  on the
  [engine comparison page](https://knotrel.github.io/knotrel-benchmarks/engines/cluster-forest-cf5-02cba68.html),
  selection guidance in
  [Choosing an engine](../choosing-an-engine.md#when-to-try-cluster-forest).

Limitations and decisions (the maintainer's, 2026-11-25, report section 7):

- **Host swap activity not verifiable; results accepted by the maintainer
  with this limitation.** It applies to every class, PASS included.
- **Default (CF6):** `compact-bfs` stays the default; `cluster-forest` stays
  opt-in and experimental.
- **Lifecycle memory:** two heap-growth checks (C3) fail on the sparse
  1 000-node graph, *reuse same* (+20.2 %) and *toggle* (+14.6 %), growth
  projected from the slope to 30 cycles. Accepted as a documented limitation;
  memory stability for those two workloads stays open. Nine RSS runs exceed
  the disclosure budget (C4).
- **Transfer to 1.1.0 (open):** 1.1.0 differs from the measured build by
  documentation and doc comments (including doctests), CI configuration,
  release checks, version lines, the console's development tooling
  (`typescript` 5.9.3 to 6.0.3) and one runtime dependency patch update of the
  server, `sonic-rs` 0.5.11 to 0.5.12 (JSON). Whether the results transfer to
  the 1.1.0 build is a separate maintainer decision; the decision record
  analyzes the `sonic-rs` change. Binary identity with the measured build and
  a new measurement of 1.1.0 are not claimed.
