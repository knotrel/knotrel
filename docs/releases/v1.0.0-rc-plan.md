# v1.0.0 release-candidate plan (roadmap 1.0.0a, R1–R3)

**Status: proposed (2026-11-22), revised the same day with the maintainer's
decisions** (§6). Items marked *decided* record those decisions; everything
else still needs approval. No tag and no publication happen in this phase.

Path: v0.9.0 (published 2026-11-22) → **v1.0.0-rc** → **v1.0.0**. The
acceptance for v1.0.0 is the roadmap's: the ten criteria of the
[readiness assessment](v1.0-readiness.md) met or explicitly disposed, and
R1–R3 complete. This plan orders the work and states what each step needs
from the maintainer.

## 2. R1 — v1.0 qualification campaign and dispositions (*decided*)

**Decisions (2026-11-22).**
- v1.0.0 gets its **own campaign** against the **latest published 0.9.x,
  frozen as the reference** (today v0.9.0), **even if the measured code is
  unchanged** from that reference.
- The campaign **reuses the existing protocol** (the v0.9.0 qualification
  protocol, itself the v0.7.0 qualification-3 method: cells, pairs,
  estimators, seeds, window multipliers, interference policy, thresholds)
  and limits its perimeter to the **relevant comparisons**. It does not
  reopen every diagnostic.
- Results and intervals are **published on the benchmark site**.
- **The v0.9.0 exceptions remain historical evidence**, for v0.9.0 only.
  Dispositions for v1.0 are decided **on the relevant results of the new
  campaign**, with **no acceptance in advance**.

**Proposed perimeter** (fixed in the campaign plan, approved before
measuring, like 0.9.6; draft: [v1.0.0 qualification plan](v1.0.0-qualification-plan.md),
proposed):

| Group | Cells | Why |
| --- | --- | --- |
| Release cells (A) | All 9 | The headline release comparison |
| Former exceptions | E1 core sparse traversal; E2 HTTP batch 256 (with its RSS supporting metric); E3 metrics overhead, lifecycle batches, sparse 10k; E4–E5 core flagged import, sparse and hub 10k | The results not PASS in 0.9.6, re-measured, not inherited |
| Concurrency (M_reg) | The 6 cells | Regression guard of v0.7.0's read-write lock |
| Feeder under load | Q1–Q5 of `docs/integrations/feeder-under-load.md`, the approved single-host protocol | Q3 stays a criterion; the R2 variant is separate and is not this campaign |
| Code changed since the reference | Every cell exercising a path changed between the reference and the candidate (none if `crates/`, `Cargo.toml`, `Cargo.lock` and `rust-toolchain.toml` are unchanged) | Changes must be qualified |
| Disclosures | C4 RSS (6 cells), `import-high` | Kept visible, disclosure category as before |

Out of the perimeter unless a code change touches them: B1–B4 lifecycle
timing beyond the cells above, B5, C1–C3, T5, Rmem, M_desc, Part 2-style
descriptive comparisons. *Clarified (2026-11-22):* the selection is
**reduced** compared with the v0.9.0 campaign, and the method of every
reused cell stays unchanged. The campaign plan maps every function changed
since the reference to the cells included or excluded, with a reason. It
also includes the cells that a collector produces with an included cell
(C1–C3 with C4, all of R and Rmem), so that nothing measured goes
unreported. The A cells use a fixed sample of 24 pairs with no interim
look, so that the stated interval coverage holds; this is a deviation from
the v0.9.0 extension rule, justified in the campaign plan. The two `hub` 10k requirements (E6) stay not
qualifiable by comparison until an atomic reference design is approved
(roadmap v1.2.0 H2); the campaign states that, without a verdict.

**After the results**, each non-PASS result gets a maintainer decision for
v1.0: accepted for v1.0 with its classification kept and disclosed, or
assigned to v1.2.0 H2 with a criterion, or fixed and re-measured.
Classifications, intervals and thresholds stay as measured. The candidate
for the campaign is frozen only after the R3 changes to release code have
landed.

**rc-blocking rule (proposed, with the maintainer's clarifications of
2026-11-22).**
- The rc is not tagged until the campaign is valid and every non-PASS
  result has a recorded disposition, as above.
- **Q3** needs both an **explicit disposition** and a **documented
  operational envelope** (the declared supported envelope, §3 "Then").
  The absence of either one blocks.
- **E6** remains **explicitly unqualified** and requires a disposition for
  1.0.
- **R2 remains diagnostic.** Not running it does not automatically block the
  rc. In that case the envelope is limited to the configuration actually
  measured, without attributing a cause to the Q3 failure.
- **No 0.9 acceptance is transferred automatically.**
- **Budget:** two separate caps, not a shared pool. The deciding blocks with
  their conformance overhead get at most 105 min; feeder under load gets at
  most 30 min.
- **Reruns:** only an infrastructure failure, unrelated to the measured code
  and recorded with evidence, allows one rerun of the affected child. A
  product crash, panic, timeout, wrong result or HTTP error is a result of
  that cell and is never repeated automatically.

## 3. R2 — #87 diagnosis: two-Mac protocol variant (proposed)

**Question.** Does the CPU load that PostgreSQL, the feeder, the writer and
the query clients put on Knotrel's host explain Q3's failure, or is the
limit inside Knotrel's host itself (lock waits, query execution)?

**What separating the loads can and cannot show.** Moving the load to a
second host changes more than CPU availability: it adds a network link in
place of loopback and removes memory-bandwidth, cache and scheduler
interference and PostgreSQL's I/O from Knotrel's host. A better catch-up
rate in that layout alone does **not** isolate CPU as the cause. The
variant therefore adds an arm that gives the CPU load back to Knotrel's host
while the rest of the layout stays separated (arm U), and the outcomes
distinguish **supported**, **insufficient evidence** and **not supported**.

**Why two machines.** macOS has no core pinning (no `taskset`/cpusets), so
the roadmap's single-host pinned variant is not available on the
maintainer's hardware.

**Hosts.**
- **Host K (Knotrel):** the Apple M3 (4P+4E, 16 GB, macOS 26.5.2), the host
  of every earlier feeder-under-load and qualification measurement.
- **Host L (load):** the MacBook Pro M4 (16 GB): PostgreSQL 18.7
  (`scripts/start-test-postgres.sh`, the 0.9.6 image digest), the
  reference feeder, the writer, the markers and the query clients.
- **Link:** direct and wired (Thunderbolt bridge or Ethernet), not Wi-Fi.
  Before and after each arm: median and p99 of 1,000 TCP round trips; the
  arm is valid only if the median is ≤ 0.5 ms.
- Knotrel binds the link address with `KNOTREL_ALLOW_NON_LOOPBACK=true`, on
  a private point-to-point link between the maintainer's two machines
  (trusted network, within the trust model).
- **Availability (*decided*):** the measurement window, with both Macs on
  AC power, idle and with no interactive use, is agreed with the maintainer
  before any measurement. The tool and protocol are prepared first.

**Build under test:** `knotrel-server` at tag `v0.9.0`. Feeder and load
tool from the `integrations/postgres-feeder` commit that adds the remote
mode below.

**Tool change before measuring** (reviewed; the single-host mode must stay
unchanged, checked by a smoke run): the load tool spawns the server on
`127.0.0.1` today. Add a remote mode that starts and stops a fresh
`knotrel-server` on host K for every observation (over SSH, protocol
settings plus the bind address and `KNOTREL_ALLOW_NON_LOOPBACK=true`),
points the feeder, clients and markers at host K's link address, samples
both hosts' CPU, and, for arm U, runs a CPU load generator on host K.

**Arms.** Only scenario L2, graph G100k, the protocol's backlog (100,000
changes) and settings; everything else as in
`docs/integrations/feeder-under-load.md`.

| Arm | Layout | Cells | Observations |
| --- | --- | --- | --- |
| S (control) | Single host, as approved for 0.9.3: everything on host K, loopback | `C` = 0, 16, 64 | 3 per cell |
| T (separated) | Knotrel on host K; everything else on host L | `C` = 0, 16, 64 | 3 per cell |
| U (CPU given back) | As T, plus a CPU load on host K equal to the non-Knotrel CPU time measured on host K in arm S for the same cell | `C` = 16, 64 | 3 per cell |

Arm U's load is a fixed number of busy-loop processes at a duty cycle
calibrated from arm S's per-process CPU samples (PostgreSQL, feeder,
writer, clients), recorded with the results. It reproduces CPU demand, not
memory or I/O behavior; that limit is stated. Order: S, T, U, all cells of
one repetition before the next, in one session. Arm S re-anchors the
variant to 0.9.6 on the same day; it is not a new Q3 verdict. Budget: 45
minutes per arm, under the existing repetition rule.

**Reported per cell:** catch-up rate (backlog events / time to `ready`),
ratio to `C` = 0 of the same layout, time to `ready`, CPU busy on both
hosts during catch-up, Knotrel's phase histograms (admission queue, lock
wait, execution per feeder job), feeder `503` refusals, link round trip.

**Decision rule (fixed before measuring).** a16 and a64 are the absolute
catch-up rates at `C` = 16 and 64 of each arm. Absolute rates are used
because the link can lower the `C` = 0 rate and raise a ratio artificially.

| Outcome | Condition (both `C` = 16 and `C` = 64) | Meaning |
| --- | --- | --- |
| **Hypothesis supported** | a(T) ≥ 2 × a(S), **and** a(U) ≤ a(S) + ½ × (a(T) − a(S)) (giving the CPU load back removes at least half of the gain), **and** host K's CPU in arm T is not saturated (median busy ≤ 80 %) | CPU demand on Knotrel's host is shown to account for most of the gap at these rates |
| **Hypothesis not supported** | a(T) < 1.2 × a(S), **or** a(U) ≥ a(S) + ¾ × (a(T) − a(S)) (giving the CPU load back keeps most of the gain) | The gap is not explained by co-located CPU demand; the limit lies elsewhere (lock waits, query execution, or something the separation removed other than CPU) |
| **Insufficient evidence** | Anything else, or a validity condition fails (link round trip, interference, repetition rule) | No conclusion on the cause; the result and its numbers are reported as they are |

**Consequences.** Q3's thresholds are unchanged in every outcome; R2 never
turns Q3 into a PASS. The declared envelope states the measured numbers of
each layout as measured, with Q3 as FAIL where it fails.
- *Supported:* H2 evaluates B2 (bounded concurrent query execution) and
  deployment guidance (source and feeder off Knotrel's host) first.
- *Not supported:* H2 starts from the phase data: B1 (queued feeder work
  passes waiting readers) if lock wait dominates, otherwise a profiling
  session (H1) before any design.
- *Insufficient evidence:* no design choice is grounded on R2; H1 profiles
  the feeder-under-load scenario first.
- If a small server-side fix follows, it may be proposed for the rc; it then
  enters the v1.0 campaign (§2) as changed code. Otherwise the fix is H2.

**Limits, stated in advance.** Two Apple-silicon Macs, one link, macOS
only, one PostgreSQL version, the protocol's rates. Host L's CPU differs
from host K's; arm S on host K keeps the reference layout as before. Arm U
reproduces CPU demand only.

**Then: the declared supported envelope (readiness criterion 4).** A
document (proposed: `docs/supported-envelope.md`) with the measured
capacity table (nodes, edges, body size, clients, rates) from the
qualification evidence, the documented head-of-line behavior, the feeder
catch-up statement from R2 and the v1.0 campaign, and the hosts and limits
behind every number. Re-measured on the release commit for 1.0.

## 4. R3 — rc gates

- **R3a threat model and `SECURITY.md`** (criterion 7): merged (#106).
  *Decided:* the reporting channel is **GitHub Private Vulnerability
  Reporting**. Enabling it on `knotrel/knotrel` and verifying it (the
  Security tab offers "Report a vulnerability"; a test report reaches the
  maintainer) is an rc gate.
- **R3b randomized soak and integration-contract traceability**
  (criterion 3): merged (#105), with the D1 fix (#104). *Decided:* the soak drives the real
  `knotrel-server` as a **child process**. The traceability table maps
  each MUST of §9 of `docs/integration-contract.md` to its tests and
  prepares R3e.
- **R3c reproducible-build check** (criterion 6): merged (#107). *Decided:*
  two separate verdicts per platform:
  - **byte-for-byte identity** of the rebuilt binary with the published one;
  - **equivalence after excluding named metadata**, listing exactly what is
    excluded and why.
  First result (macOS, v0.9.0): code and data identical, the Mach-O linker
  UUID (`LC_UUID`) differs, so **not byte-for-byte identical**; equivalent
  after excluding the UUID. The UUID difference and its cause are
  documented. On GitHub's runners (2026-11-22): Linux **byte-identical**;
  macOS equivalent after excluding the same metadata (#109). The gate
  closes after the run on the release candidate against its dry-run bundle.
- **R3d contract freeze review** (criterion 1): every public Rust item and
  HTTP route/field/error code/variable/metric is **stable**,
  **experimental** or **internal**, against `docs/stability.md` and the
  `API compatibility` CI job; it closes the remaining items of the
  criterion (the broken relative links in `integration-contract.md`, the
  core README's "pre-1.0" wording).
- **R3e independent review of the whole 1.0 contract set** (criterion 9).
  *Decided:* an **AI review, separate from the implementation** (run by an
  agent that did not write the reviewed changes, on the documents and code
  themselves, not summaries), **declared explicitly as an AI review**, with
  every finding and its resolution tracked. It is **not** presented as a
  human audit or a security certification.
- **Criterion 8:** document macOS runner queueing as an infrastructure limit
  (the last open item); green CI on the rc commit.

## 5. Not in this phase

No tag (`v1.0.0-rc.*` or otherwise), no GitHub release, no crate or console
publication, no benchmark-repository tag. When the rc is considered, the
rc-blocking rule of §2 applies: a valid campaign, a disposition for every
non-PASS result, a disposition and a documented envelope for Q3, and a
disposition for E6. R2 not having run is not by itself blocking.
