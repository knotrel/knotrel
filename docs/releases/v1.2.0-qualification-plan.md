# v1.2.0 release qualification — plan

**Status: Approved by the maintainer (2026-11-27). This is the frozen
protocol of the v1.2.0 release qualification
([#182](https://github.com/knotrel/knotrel/issues/182)).** The campaign is
frozen with `results/v1.2.0-qualification/FREEZE.json` in knotrel-benchmarks.
No rule, margin, cell, size or order changes after the first observation.

The maintainer's instruction (2026-11-27) fixes these points:

- freeze the actual candidate against `v1.1.0`, and derive the matrix from
  the diff under the per-release policy
  ([#186](https://github.com/knotrel/knotrel/issues/186), knotrel-benchmarks
  `docs/methodology.md`, "Per-release measurement policy");
- include the bidirectional BFS
  ([#196](https://github.com/knotrel/knotrel/pull/196)) and
  `B4-http-ops-atomic-compact-bfs-hub-10000` as a deciding cell;
- keep the written disposition of the hub 10k `events` requirement
  (not qualified);
- record the campaign's own budget before collection;
- run the initial checks, the collection and the analysis without further
  approval, and report the Q3 verdict;
- if Q3 is FAIL, return to the B2 decision of
  [#87](https://github.com/knotrel/knotrel/issues/87).

Tagging and publication are a separate decision.

## 1. Purpose

Qualify v1.2.0 against v1.1.0 in the areas the release changes, and freeze
the candidate commit, binaries and settings for the external comparison
(knotrel-benchmarks#15). The external comparison is not a release gate.

Failures and inconclusive results are reported as such. A REGRESSION, a FAIL
or an INCONCLUSIVE result is never relabelled.

cells are re-qualified on the release commit. This plan does not decide the
transfer; the release decision does.

## 3. Scope from the diff `v1.1.0..candidate`

`git diff --stat v1.1.0 9faf168` touches seven files. Under the scope rule,
only one is a measured area:

| Area (policy) | Change | In scope |
|---|---|---|
| `crates/*/src` | `crates/knotrel-core/src/lib.rs`: `Graph::connected` becomes a bidirectional BFS (#196, adopted by its impact estimate, knotrel-benchmarks#47). Answers, errors and the O(V + E) bound are unchanged. | **Yes** |
| `crates/*/tests`, `docs/**` | tests and documents | No (not executed code) |
| `Cargo.lock` | unchanged | No |
| toolchain | unchanged (1.100.0) | No |
| server configuration defaults | unchanged | No |
| `integrations/*` (feeder) | unchanged | No |

**Callers of `Graph::connected`**, so every path the change reaches:

- `ConnectivityGraph` with `EngineConfig::CompactBfs` (core plain engine);
- `LifecycleGraph` with `compact-bfs`: its engine is a `ConnectivityGraph`,
  so lifecycle queries reach the same function;
- the server's `connected` operations (`/v1/batch`, plain and lifecycle
  topologies) with `compact-bfs`, the default engine;
- the feeder deployment's query load (block Q), served by `compact-bfs`.

**Not reached:**

- `compact-workspace` (`connected_with_workspace`, unchanged);
- `ett`, `hdt` and `cluster-forest`;
- every mutation (`link`, `cut`, lifecycle commands), except where a cell
  mixes mutations with queries.

Under the policy's "Sentinel set: none", unchanged areas get no cells. They
get the written dispositions of section 7.

## 4. Matrix

The comparisons against v1.1.0 are **regression checks**: interval of
`ln(candidate / v1.1.0)` (throughput: inverted), classes of section 6.1.
B4 and Q are absolute criteria on the candidate, with the release's own
thresholds, unchanged.

### 4.1 Tier 1

- **V1 (delegated), the frozen v1.0.0 experiment A protocol.** B = v1.1.0,
  C = the candidate, with the 9 qualification cells of `run_p0_aa.py`:
  - core sparse traversal 10k and core sustained churn 10k, each for
    `compact-bfs` and `compact-workspace`;
  - HTTP standalone batch b1, b8, b64 and b256;
  - HTTP lifecycle small.

  The batches interleave `link`, `connected`, `cut` and `connected`, and the
  lifecycle scenario measures query latency, so the request path changed.
  This block therefore re-measures the CF5 D3 carried items #1–#3 (#180
  ledger): b1 `request_latency_p99_ns` (UNRESOLVED), b64
  `sampled_max_rss_bytes` (UNRESOLVED) and lifecycle small `time_to_ready_ms`
  (INCONCLUSIVE_DISCLOSED).

  Method: two plans of 12 pairs per cell (`run_p0_aa.py --execute`, block 1
  then block 2), with no analysis in between. Session seeds are 182110,
  182111 and 182112 (block 1), and 182120, 182121 and 182122 (block 2). It is
  analyzed once by `analyze_v100q_a.py` with the v1.0.0 A rules. The
  `compact-workspace` cells are part of the protocol's fixed cell set. Their
  code is unchanged, and they are reported as such.
- **V2 (paired), server under contention.** The 6 v1.0.0 M_reg cells, run
  with `compact-bfs` by the contention probe on the candidate server and on
  the v1.1.0 server. Lifecycle is off in 4 cells and on in 2; there are
  standalone and source-managed variants. Metrics: `requests_per_s`
  (throughput, 10 %) and `latency_ns.p99` (tail, 25 %).

### 4.2 Tier 2

- **Q (delegated), feeder under load: final Q3 verdict (#87 step 3).** This
  is the v1.0.0 block Q runner (`run_v100q_q.py`), unchanged:
  - candidate side: the seven cells of the approved protocol
    (`docs/integrations/feeder-under-load.md`) on the candidate server, with
    the server's default engine (`compact-bfs`);
  - Q5 reference arm: L1 G100k C=16 and C=64 on the **v1.1.0** server;
  - 3 observations per cell over three rounds, with the side that goes first
    alternating; the same feeder (built at the candidate), load tool and
    PostgreSQL 18.7 for both sides.

  Criteria, with the protocol's thresholds unchanged:
  - Q1: marker lag p99 ≤ 1 s and maximum ≤ 3 s (L1 G100k C=16);
  - Q2: no growing lag (all L1 cells);
  - **Q3: catch-up rate with C=16 ≥ 50 % of the C=0 rate, and with C=64
    ≥ 25 % (L2 G100k);**
  - Q4: time to `ready` ≤ 60 s (L2 G100k C=64);
  - Q5: query throughput ≥ 90 % and client p99 ≤ 125 % of the v1.1.0
    reference (L1 G100k C=16 and C=64).

  The evaluation is `evaluate_v100q_q.py`. PostgreSQL exists only while Q
  runs, through the collector `results/v1.2.0-qualification/run_q.sh`, which
  manages the Docker Desktop and container lifecycle as CF5 S3 did; the admin
  URL is never written. Q's own cap is 45 minutes, against an estimate of
  about 27 one-minute steps. If the cap is reached, Q is NONCONFORMING: the
  completed observations are kept, and criteria without their observations
  get no verdict.
- **B4 (delegated), lifecycle cost on the candidate.**
  `run_lifecycle_qualification.py --profile final --only B4
  --lifecycle-engines compact-bfs --equivalent-references
  --atomic-references`, with order seed 182400. That is 38 cells:
  - the 37 B4 cells of the v1.0.0 qualification;
  - plus `B4-http-ops-atomic-compact-bfs-hub-10000` (knotrel#180, decisions
    M1(b)–M6).

  Window multipliers: the frozen v1.0.0 factors
  (`results/v1.0.0-qualification/window-multipliers-q3.json`) for every
  timed B1–B4 cell of the scope (74; the collector requires a factor for each
  before `--only` applies, as in v1.0.0), plus factor 1 for the atomic cell,
  the factor of its `ops` hub counterpart. They are in
  `results/v1.2.0-qualification/window-multipliers.json` (75 entries).

  Rules (unchanged, `analyze_lifecycle_qualification.py`): 2 warmup and 12
  pairs per cell, interval `[r(3), r(10)]`, PASS if the upper bound
  ≤ ln(1 + t), REGRESSION if the lower bound > ln(1 + t), otherwise
  INCONCLUSIVE; TIMER_LIMITED when either arm's median window is below 1 ms.

  The cells are classed as follows (sets recorded in the matrix):
  - **Deciding (23):**
    - `B4-http-ops-atomic-compact-bfs-hub-10000` (tolerance 25 %), with the
      untimed gate check and its negative control as conformance conditions
      (M6);
    - the v1.0.0 deciding set (22): every B4 cell except the v1.0.0
      descriptive cells and the two cells that are not atomicity-equivalent.
  - **Descriptive (15):**
    - the 13 v1.0.0 descriptive cells;
    - the two `-equivalent-` hub 10k `ops` and `events` cells (M4).
  - **No verdict on the requirement (4, within the descriptive cells):** the
    frozen and `-equivalent-` hub 10k `ops` and `events` cells, as in v1.0.0
    E6. The `ops` requirement is decided by the atomic cell; `events` keeps
    its disposition (section 7).
- **K2 (paired), core queries at scale.** `cf5-core staged` with
  `connectivity-compact-bfs`, degrees 4 and 16 × 10⁴, 10⁵ and 10⁶ vertices,
  seed 42. That is 6 cells, with metrics `query_ns` and `update_ns` (time,

  The arms are the same tool source (this campaign's tooling commit), built

- **K1 (paired), core workload families.** The connectivity harness at the

  The families are:
  - the four one-shot families and the two sustained ones, at 10⁴ and 10⁵;

## 5. Method

As CF5 (`docs/releases/v1.1.0-cf5-qualification-plan.md` sections 5, 6 and
6.1), executed by `run_cf5.py` with this campaign's matrix:

- **Paired blocks (V2, K1, K2):**
  - each observation runs in a fresh process (server blocks: a fresh
    server);
  - 2 warmup pairs, then a fixed n = 24, with the order inside the pair
    balanced 12/12 by a frozen seeded schedule; there is no interim
    analysis and no extension;
  - the interval is `[r(7), r(18)]` (coverage 97.73 %);
  - the order seed is derived from the matrix hash and the candidate SHA, so
    it cannot be chosen.
- **Measurement limit (CF5 §6.1)**, with the CF5 calibration
  (`results/v1.1.0-cf5/timer-calibration`), same host and toolchain: a class
  that would change within the limit is TIMER_LIMITED. It applies to V2,
  K1 and K2. V1, Q and B4 keep their own rules.
- **Correctness gate:**
  - every core observation checks its answers against the workload oracle;
  - every arm checks the engine it ran;
  - the arms of a cell must run the same inputs;
  - server observations require `errors == 0`.

  A failed gate, a non-zero exit or unparsable output is a FAIL of the
  campaign: it stops, and the defect returns to development. A timeout or a
  missing executable is an infrastructure failure: the observation is
  retried once.
- **Tier-1 smoke:** before any measured pair, every distinct arm runs once
  with its gates.
- **Recorded:** the record holds:
  - the matrix hash, the tool map and the executable hashes;
  - the checkout SHAs (candidate, baseline, tooling, A harness) and the
    lockfile hashes;
  - the host description, before and after every block;
  - **cumulative swap counters** (`vm_stat` `Swapins` and `Swapouts`),
    before and after the session window (CF5 D1);
  - `sysctl vm.swapusage`.

## 6. Classification and consequences

### 6.1 Regression checks (V1, V2, K1, K2)

The CF5 §7.1 table applies, with v1.1.0 in place of v1.0.0:

| Class | Rule | Consequence |
|---|---|---|
| PASS | `hi ≤ ln(1 + t)` | none |
| REGRESSION | `lo > ln(1 + t)` | blocks the release until the cause is fixed and the cell re-qualified on a new candidate, or the maintainer accepts it explicitly, named in the release notes |
| INCONCLUSIVE | otherwise | no evidence either way; needs a maintainer disposition (accept with disclosure, or a targeted follow-up on the same candidate); never rerun inside this campaign |
| TIMER_LIMITED (V2, K1, K2) | the class would change within the measurement limit | as INCONCLUSIVE |

V1 keeps the frozen v1.0.0 A analysis (no TIMER_LIMITED, REPORT_ONLY link/cut
p99 of the core cells). Faster results are reported with their intervals.
They are never a criterion.

### 6.2 B4

Deciding cells as section 4.2:

- REGRESSION blocks as in section 6.1;
- INCONCLUSIVE and TIMER_LIMITED need a disposition;
- a failed gate check or negative control of the atomic cell stops its probe
  and is a FAIL.

The publishable wording, if `ops-atomic` passes, is the one approved in
`docs/design/hub-10k-lifecycle-reference.md`.

### 6.3 Q

Each criterion is PASS or FAIL as computed. A criterion whose observations
are missing gets no verdict, and that is never a PASS.

**Q3** is reported with both conditions: the C=16 share against 50 %, and the
C=64 share against 25 %.

- If Q3 is PASS, #87 can close, together with the #180 ledger row.
- If Q3 is FAIL, it stays FAIL with unchanged thresholds, and the next step
  is the **B2 decision of #87**: bounded concurrent query execution, designed
  and measured as an impact estimate against Q1–Q5. The report names that
  step.

### 6.4 Not merged

REGRESSION, FAIL, INCONCLUSIVE and TIMER_LIMITED are listed separately in
the report and in the release notes; nothing is pooled or dropped.

## 8. Execution order and the budget

**Budget (this campaign's own): recorded in `FREEZE.json` and in the matrix
(`rules.cap_hours`) before the first observation.** It is derived from a
preparatory duration trial (`run_cf5.py --preparatory`, 2 pairs, no smoke;
never used for decisions), with a margin of about 30 %. The value and its
derivation are added to section 11 before the freeze.

Blocks run in this order of priority, one after another; pairs interleave
only within a block, so the cap cuts the last blocks:

1. **Tier 1:** smoke, V1, V2.
2. **Tier 2:** Q, B4, K2, K1.

The delegated blocks run at their place, under the same deadline, through
their own collectors. A collector that has started runs to its end. A
crashed collector is rerun once from scratch. A second failure stops the
campaign.

**At the cap:**

- the pair in progress completes, and no new step starts;
- a cell with fewer than 24 pairs is INCOMPLETE (no class); a cell not
  started is NOT_RUN;
- both are missing evidence, never a result.

There is no second session (`second_session_cap_hours` 0).

## 9. Attempts and validity

- **Attempts:** at most two. The second runs from scratch, and only if the
  first is NONCONFORMING (interrupted, runner error, failed conformance).
  Each attempt has its own campaign directory, built by
  `prepare_v120q.sh CAND FREEZE ATTEMPT`.
- **Freeze check:** the freeze commit may only add `FREEZE.json`, which names
  the candidate, the tooling commit and the matrix hash. The runner refuses
  to start when the candidate checkout or the matrix differs, or when a
  checkout is dirty.
- **Conformance:**
  - SHAs and binary hashes match the record;
  - AC power throughout;
  - no thermal warning;
  - **no swap activity**: `Swapins` and `Swapouts` unchanged over the
    window.

  A failed check makes the attempt NONCONFORMING, and no classes are
  published from it.

## 11. Budget estimate

From the preparatory duration trial of 2026-11-27: 68 min at 2 pairs per cell, no swap activity,
deciding nothing. It ran against the pre-freeze candidate 9faf168 and tooling 6b47a04.

| Block | Trial | Frozen run |
|---|---|---|
| V1 | 27 min (full plan) | 27 min |
| Q | 29 min | 45 min (Q cap, worst case) |
| B4 | 2 min (full `final` profile) | 2 min |
| V2, K2, K1 | 639 s at 2 pairs | 139 min (× 13 for 26 pairs) |
| Smoke and setup | — | 5 min |
| **Total** | 68 min | **218 min (3.6 h)** |

With a 30 % margin this is 4.7 h, so the **cap is 5.0 host hours** for the single session
(`rules.cap_hours`; derivation in knotrel-benchmarks `results/v1.2.0-qualification/BUDGET.md`).
There is no second session. Cells still incomplete at the cap are `INCOMPLETE`.
