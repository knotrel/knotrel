# Knotrel v0.5.0 Release Notes — Node & Edge Lifecycle (draft)

**Status: draft.** v0.5.0 is not released. Implementation, documentation and
independent review are recorded below; the performance qualification result,
CI on the release commit, packaging checks and maintainer approval are listed
under [Outstanding release gates](#outstanding-release-gates).

## Scope

v0.5.0 delivers roadmap **M10**: reversible node activation, reversible edge
enabling and permanent node removal. It is **opt-in**. With the default
configuration, the server, the HTTP API, the feeder protocol and the core
`ConnectivityGraph` behave as in v0.4.0.

Not in this release: local persistence and fast recovery (deferred to an
unassigned release), multiple graphs, electrical power-flow simulation and
concurrency redesign.

## What is new

**Model.** A graph with lifecycle support keeps **registered** topology with a
node-active flag per node and an edge-enabled flag per edge. Connectivity uses
the **effective** graph: an edge counts only when it is registered, enabled and
both endpoints are active. See the [lifecycle contract](../topology-lifecycle.md).

**Core (`knotrel-core`).** New `LifecycleGraph`, `NodeSpec`, `EdgeSpec`,
`EdgeState` and non-exhaustive `LifecycleError`:
- `set_node_active`, `set_edge_enabled`, `remove_node`;
- `node_active`, `edge_state` and the counts `active_node_count`,
  `enabled_edge_count`, `effective_edge_count`;
- `try_from_topology` for bulk construction with flags;
- `engine_vertex_count` and `storage_stats` (`LifecycleStorage`) for
  storage diagnostics: logical sizes, retained capacities and retired engine
  slots;
- the existing `add_node`, `link`, `cut` and `connected` on registered
  topology.

All three engines are supported through the same facade. `Graph`,
`ConnectivityGraph` and `GraphError` are unchanged.

**Server (`knotrel-server`).** `KNOTREL_TOPOLOGY_LIFECYCLE=true` (or
`ServerConfig::with_topology_lifecycle`) enables:
- direct operations `set_node_active`, `set_edge_enabled`, `remove_node`,
  `node_state` and `edge_state` in `/v1/operations` and `/v1/batch`;
- feeder events with the same three mutations, whose flags are part of
  duplicate detection;
- import entries `{"node":"…","active":false}` and edges with
  `"enabled":false`;
- lifecycle counts in `/v1/stats` and the import response, and
  `"topology_lifecycle": true` in `/v1/info`;
- metrics: new `op` values in `knotrel_graph_operations_total`, and gauges
  `knotrel_graph_active_nodes`, `knotrel_graph_enabled_edges` and
  `knotrel_graph_effective_edges`.

New error codes: `unknown_edge` and `topology_lifecycle_disabled`.

**Example.** The power-grid tutorial gains a lifecycle scenario
(`examples/power-grid/lifecycle_demo.py`): deactivate a substation, disable a
connection while it is inactive, reactivate it with that connection still
disabled, then remove and re-create it without its old connections.
Connectivity is still not power flow.

## Compatibility and migration

**Default configuration: no client-visible change,** with two additive
exceptions that apply in every configuration:
- `knotrel_feeder_rejections_total` has one more `code` series,
  `topology_lifecycle_disabled`, at zero in source-managed mode;
- the error-code vocabulary gains `unknown_edge` and
  `topology_lifecycle_disabled`. Without lifecycle support, a client only
  receives `topology_lifecycle_disabled`, and only when it sends a lifecycle
  request.

**Requests that changed behavior without lifecycle support.** The five new
operation names, the three new event names and flagged import entries were
previously rejected as malformed (422 `invalid_request`). They are now
recognized and rejected with 409 `topology_lifecycle_disabled`.

**Flagged legacy feeder events.** An `add_node`, `link`, `cut` or `progress`
event carrying `active` or `enabled` is still 422 `invalid_request`, but it is
now detected during per-event prevalidation instead of while parsing the
body. When the same request also fails a whole-request check (session,
lease, generation or source), that error is now returned first, and the 422
message text differs. A JSON `null` flag is always 422, as before.

**Enabling lifecycle support:**
- `node_count`, `edge_count`, `knotrel_graph_nodes` and `knotrel_graph_edges`
  count **registered** objects, including inactive nodes and disabled edges.
  Use the new counts for active or effective topology.
- `KNOTREL_MAX_NODES` and `KNOTREL_MAX_EDGES` bound registered objects.
  Deactivating or disabling frees no capacity; only `remove_node` and `cut` do.
- `connected` returns `false` when an endpoint is inactive, including
  `connected(n, n)`. Unknown nodes are still 404 `unknown_node`.
- `add_node` never reactivates an inactive node, and `link` never re-enables a
  disabled edge; use the explicit setters.
- In source-managed mode, the feeder must send the flags in every
  authoritative import and use lifecycle events for changes. A restart still
  loses all in-memory state, including flags.

**Embedded Rust users.** Lifecycle methods that return `Err` made no change.
A panic during a mutation leaves a `LifecycleGraph` unspecified; discard it.

## Costs and resource limits

- Deactivating, reactivating and removing a node cost work proportional to its
  registered degree, plus one engine update per effective incident edge.
  Removal also edits each neighbor's incident list. **No lifecycle operation
  has a logarithmic bound in general.**
- Engines do not delete vertices. A removed node leaves an isolated engine
  slot, reused if the same ID returns. When unused slots exceed
  `max(registered nodes, 1024)`, the engine is rebuilt from the catalog: that
  removal costs a whole-graph rebuild under the graph lock, `O(1 + E/V)`
  engine insertions amortized per removal.
- Lifecycle mode stores registered topology in a catalog besides the engine's
  effective graph. Measured after building 100k nodes: 2.45× the plain
  engine's heap on `compact-bfs`, 1.24× on ETT, 1.16× on HDT.
- Deactivation and removal cut incident edges in descending neighbor order;
  on `compact-bfs` this avoids shifting the node's adjacency vector.

## Performance qualification

**Outcome: not passed unconditionally; owner decisions pending.** Candidate
`6494253` (run 2 of the frozen protocol in knotrel-benchmarks
`results/lifecycle-qualification-v0.5.0/`; host Apple M3, macOS 26.5.2,
rustc 1.100.0). The v0.4.0 maintainer waivers do not carry forward.

**Existing behavior against v0.4.0, lifecycle disabled** (v0.4.0 design and
rules): 4 PASS, 2 INCONCLUSIVE_DISCLOSED (core sparse traversal with
`compact-workspace` +7.94% [+2.16%, +11.31%]; HTTP startup −1.93%
[−15.62%, +23.91%]), **3 UNRESOLVED** (HTTP batch 1 request p99 +17.04%
[−27.31%, +68.98%]; sampled RSS of batches 64 and 256, upper bounds 22.1% and
21.0% against 20%), no REGRESSION.

**Lifecycle cost against semantically equivalent references:** 157 PASS,
9 REGRESSION, 1 INCONCLUSIVE.
- Lifecycle operations, lifecycle HTTP batches and feeder events: all PASS
  against equivalent application-side code. Opt-in cost on legacy operations:
  all within budget (largest: ETT, +30.6%).
- REGRESSION: `remove_node` of nodes with degree ≥ 4,096 on ETT and HDT,
  1.3×–1.6× the application-side reference; flagged imports, 2.0×–7.2× a
  plain import of the effective graph (budget 2×).
- INCONCLUSIVE: metrics-enabled lifecycle batches on `compact-bfs`,
  +6.00% [+0.64%, +9.37%] against a 6% budget.

**Memory and sustained resources:** after building 100k nodes, lifecycle mode
used 2.45× the plain engine's heap on `compact-bfs`, 1.24× on ETT and 1.16× on
HDT (budget 3×). Under 30 cycles of churn, engine slots and logical counts
stayed exactly as specified, and the catalog did not grow. **18 heap-growth
checks failed**, mostly HDT and ETT under same-ID and toggle churn (for
example HDT 99 → 252 MiB at 100k nodes); the application-side reference grew
equally, so this is engine growth under sustained churn. RSS exceeded its
disclosure budget in 29 of 45 cells.

A first run on candidate `ea12706` found 31 regressions, mostly from two
facade defects fixed in `6494253`; its evidence is preserved and reported.
