# Knotrel v1.0.0 Release Notes — Stable Contract

**Status: released 2026-11-24.** Stable contract for the 1.x series.
Performance qualification accepted with exceptions, transferred from the
measured candidate `0c49b2a` under a documented waiver (see
[Performance qualification](#performance-qualification)); feeder catch-up
under query load (Q3) is a declared limitation. No release candidate was
published.

## Scope

v1.0.0 freezes the contract. From this release, the stable surfaces in
[stability classes](../stability.md) follow the [compatibility
policy](../compatibility.md) for the whole 1.x series: the public Rust API of
`knotrel-core` and `knotrel-server`, the `/v1` HTTP API and feeder protocol,
the stable `KNOTREL_*` variables and the stable metric families. Breaking
changes need a major release; the exceptions approved for 1.0.0 are listed
below. Lockstep: `knotrel-core`, `knotrel-server` and the console share the
version 1.0.0 and one tag, `v1.0.0`.

v1.0.0 adds no new graph feature. Its changes since v0.9.0 are the contract
freeze (with its approved breaking changes), fixes found by the randomized
soak and by the independent AI review of the contract set (R3e), and release
and security tooling.

## What is new since v0.9.0

**Contract freeze ([freeze review](v1.0-contract-freeze-review.md), maintainer
decisions of 2026-11-22).**
- Public Rust API frozen and checked in CI: a committed public API snapshot
  (`docs/api/public-api-*.txt`) with a classification of every public item,
  cross-checked against `docs/stability.md` by `scripts/public-api.py` in the
  `public API` job ([#113](https://github.com/knotrel/knotrel/pull/113)).
- `#[non_exhaustive]` on `EngineConfig`, `GraphError`, `IncidenceError`,
  `EdgeState` (core) and `Phase` (server); `EdgeState::new` for construction
  outside the crate. `ServerMode`, `ShutdownOutcome`, `GraphLimits`,
  `NodeSpec` and `EdgeSpec` are frozen exhaustive (#113).
- `router_with_lifecycle` is Stable, with its readiness behavior during the
  drain documented; `axum` 0.8 and `tokio` 1 are documented public
  dependencies of the stable server API (#113).
- Every ETT and HDT interface, `LifecycleGraph::storage_stats` and
  `LifecycleStorage` are Stable as documented guarantees ("stable interface,
  experimental engine"); `ett` and `hdt` remain experimental engines
  ([#118](https://github.com/knotrel/knotrel/pull/118)).
- Items narrowed from Stable to Experimental are listed in
  [stability.md](../stability.md#reclassified-from-stable-to-experimental)
  (inspection setters and route labels, `KNOTREL_FEEDER_RESERVED_JOBS`
  constants, three inspection error codes and the `/v1/info` field
  `inspection`).
- Admission metrics labelled by lane
  ([#112](https://github.com/knotrel/knotrel/pull/112)), feeder admission
  codes, `too_many_connections` in the error-code enum and enforced input byte
  limits ([#114](https://github.com/knotrel/knotrel/pull/114)): see
  Compatibility.

**Server fixes.**
- **D1** ([#104](https://github.com/knotrel/knotrel/pull/104)): a feeder event
  with `delivery_sequence: 0` before the first applied event of a generation
  panicked the graph worker and left the server unavailable until restarted.
  It is now rejected with `409 unverifiable_duplicate` without state change,
  as documented. Found by the randomized soak.
- **B1** ([#123](https://github.com/knotrel/knotrel/pull/123)): a barrier
  that omits `barrier_source_position` (or sends `null`) validates only the
  delivery sequence, as OpenAPI and `http-api.md` document; before, it always
  failed with `409 barrier_position_mismatch` on an initialized graph.
- **B8** (#123): while draining, only `GET` and `HEAD` on `/health`, `/ready`
  and `/metrics` are answered; other methods on those paths get
  `503 shutting_down` (with `Connection: close`) instead of `405`.
- **B10** (#123): feeder and inspection error messages no longer quote
  client-supplied strings (`If-Match`, `source_id`, `source_epoch`,
  `event_id`, `instance_id`, `graph_id`, positions, unknown operation and
  parameter names). Server state is still quoted. Message texts are internal;
  `http-api.md` and the [threat model](../threat-model.md) (T1.9) state the
  property precisely.
- **B11** (#123): an inspection path segment that is not valid UTF-8
  (`/v1/nodes/{node}`, `/v1/nodes/{node}/edges`) gets the JSON error envelope,
  `422 invalid_request`, or `409 inspection_disabled` when inspection is off,
  instead of a plain-text `400`.
- **N6** ([#126](https://github.com/knotrel/knotrel/pull/126)): `413` only
  when a body exceeds its limit; any other body read failure is
  `400 invalid_request` (see Compatibility).
- **N5a** ([#134](https://github.com/knotrel/knotrel/pull/134)): on
  `POST /v1/feeder/barrier` the recovery fence is checked right after the
  desynchronization check and before the source-position bound and the
  sequence and position checks, as integration contract §4.3 requires. A
  barrier under a fenced epoch now answers `409 fenced_feeder_session` even
  when its sequence or position is also wrong (see Compatibility).

**Documentation corrections of the contract (R3e, B3–B7, B9,
[#122](https://github.com/knotrel/knotrel/pull/122)).** The integration
contract no longer documents import body precondition fields (`If-Match` is
the only carrier); `generation` is a JSON integer and `source_epoch` a JSON
string; `instance_id` is an opaque string from `GET /v1/info` and
`GET /v1/stats`; the `KNOTREL_MAX_IMPORT_BODY_BYTES` upper bound is 536870912
(512 MiB); **B7**: `KNOTREL_MODE=source-managed` is documented as a stable
alternative spelling of `source_managed` (accepted before, now promised); the
HDT storage payload fields document that hashed containers are counted.
**S10** (#134): `ServerInfo.experimental` (`GET /v1/info`) is defined as the
engine qualification, not a stability class: it may change from `true` to
`false` in a minor release when an engine is promoted, never from `false` to
`true` for an existing engine (OpenAPI, `http-api.md`, compatibility.md §2.2,
stability.md, Rust docs). **N5b** (#134): integration contract §3.1 states that
the import checks the `X-Knotrel-Instance-Id` header before the import permit
and the body `instance_id` after the permit and the body parse. Wire behavior
is unchanged by these corrections.

**Correctness and release tooling.**
- Randomized feeder/restart soak against a reference model
  (`crates/knotrel-server/tests/soak.rs`; short variant in CI on all three
  platforms) and §9 traceability:
  [criterion 3 evidence](v1.0-criterion-3-evidence.md)
  ([#105](https://github.com/knotrel/knotrel/pull/105)).
- Reproducible-build check of the release binary, Linux and macOS
  ([reproducible builds](reproducible-build.md),
  [#107](https://github.com/knotrel/knotrel/pull/107),
  [#109](https://github.com/knotrel/knotrel/pull/109)).
- The OpenAPI compatibility check also flags removed response enum values
  (error codes, engine values, readiness statuses) and dropped `const`s
  ([#121](https://github.com/knotrel/knotrel/pull/121)).
- [Threat model](../threat-model.md) for the supported exposure, with each
  mitigation mapped to its test, and `SECURITY.md` naming GitHub Private
  Vulnerability Reporting as the channel
  ([#106](https://github.com/knotrel/knotrel/pull/106)); refreshed for the
  1.0 contract, accepted pending maintainer review.

**Console 1.0.0.**
- Every console container value must be a single line: a value with a line
  feed or a carriage return stops the container at startup (#132; it could
  otherwise render extra nginx directives).
- Container variables move to the `KNOTREL_CONSOLE_` namespace:
  `KNOTREL_UPSTREAM` becomes `KNOTREL_CONSOLE_UPSTREAM` and
  `KNOTREL_UPSTREAM_TIMEOUT` becomes `KNOTREL_CONSOLE_UPSTREAM_TIMEOUT`; the old
  names remain deprecated aliases for 1.x
  ([#128](https://github.com/knotrel/knotrel/pull/128), see Compatibility).
- The Performance page shows one admission saturation row per lane (one
  unlabelled row for servers before 1.0.0); `too_many_connections` is a known
  error code (#112, #114).
- Supported server range now `>=0.9.0 <1.0.0 || >=1.0.0-rc.1 <1.1.0`: 0.9.x,
  the 1.0.0 release candidates from `rc.1`, and 1.0.x (see Compatibility).

## Compatibility

### Approved breaking changes and exceptions for v1.0.0

Approved by the maintainer without the deprecation window of
[compatibility.md §4](../compatibility.md#4-deprecation); declared in
[compatibility.md §3](../compatibility.md#3-what-compatible-means) and, for
OpenAPI, in `docs/api/approved-breaking-changes.yaml`.

- **Feeder admission code `busy`** (decision 4, #114): an exhausted feeder
  admission lane (data lane: `POST /v1/feeder/events`, `/barrier`, `/gap`;
  control lane: `/session`, `/heartbeat`) answers `503 busy`, as the shared
  lane does, instead of `503 import_in_progress`. `import_in_progress` is now
  returned only by `POST /v1/feeder/import` while another import runs.
  Clients that retried on `import_in_progress` from those five routes retry
  on `busy`.
- **Input byte limits** (decision 6, #114): source positions (event
  `source_position` and `prev_source_position`, import `source_position`,
  `barrier_source_position` when present) are 1 to 256 bytes of UTF-8, and
  `event_id` is at most 64 bytes, counted in bytes. A request whose only fault
  is a value outside them gets `422 invalid_request` and changes nothing; the
  bound is checked at the existing validation step, not first. Before, empty
  positions and over-long import and barrier positions were accepted.
  OpenAPI gains `minLength`/`maxLength` (nine entries in
  `approved-breaking-changes.yaml`; OpenAPI counts characters while the
  server counts bytes); the tenth v1.0.0 entry, `feeder_epoch` with
  `FeederU64`, is a schema correction, not a behavior change (decision 10).
  The OpenAPI compatibility check against v0.9.0 reports exactly these 10
  approved breaking changes.
- **400 versus 413 on import body read errors** (backlog N6, approved
  2026-11-23, #126): on `POST /v1/feeder/import`, `413 payload_too_large` now
  means only that the body exceeds `KNOTREL_MAX_IMPORT_BODY_BYTES`, by its
  declared `Content-Length` or while it is received (chunked included). A
  body that cannot be read to its end for another reason (client abort,
  malformed chunked encoding, receive error) answers `400 invalid_request`
  ("request body could not be read"), as the other JSON routes now do with
  the same fixed message. Before, every import body read failure answered
  413. Feeders must not shrink an import after a 400. The import still counts
  as `payload_rejected` in `knotrel_imports_total` (or `abandoned`).
- **Per-lane metric labels** (decision 7, #112): `knotrel_graph_jobs_outstanding`,
  `knotrel_graph_job_capacity` and `knotrel_requests_rejected_total` gain a
  `lane` label (`shared`, `feeder_data`, `feeder_control`, `import`, and
  `none` for `shutting_down` and `unavailable` rejections). Queries and alerts
  that match these series without aggregating over `lane` must be updated;
  the bundled alert rules are.
- **`#[non_exhaustive]`** (decisions 1–3, #113) on `EngineConfig`,
  `GraphError`, `IncidenceError`, `EdgeState` and `Phase`: exhaustive `match`
  outside the crates needs a wildcard arm, and `EdgeState` is built with
  `EdgeState::new`. Declared in the crates' `cargo-semver-checks`
  configuration and in `docs/api/public-api-policy.toml`, valid for v1.0.0.
- **Barrier recovery fence before sequence and position** (review N5a,
  approved 2026-11-23, #134): on `POST /v1/feeder/barrier` a barrier under a
  fenced epoch (`feeder_epoch <= last_expired_epoch` after a lease expiry)
  that also has a premature or older sequence, a mismatched position or an
  out-of-bounds position now answers `409 fenced_feeder_session`; before, it
  answered `409 barrier_not_reached`, `409 superseded_barrier`,
  `409 barrier_position_mismatch` or `422 invalid_request`. Guaranteed
  precedence: failed, session and lease, generation, uninitialized (B3, B4),
  desynchronized (B5), recovery fence, position bound, B8, B9, B7, then
  B1/B2. Every rejection still leaves the state unchanged. Declared in
  [compatibility.md §3](../compatibility.md#3-what-compatible-means); no
  OpenAPI schema change.
- **Narrowed to Experimental:** the items in
  [stability.md](../stability.md#reclassified-from-stable-to-experimental),
  listed above (decision 8).

### Other behavior changes

- **B1:** a barrier without `barrier_source_position` is accepted when its
  delivery sequence matches (it was always refused before; documented
  behavior).
- **B8:** `503 shutting_down` instead of `405` for a non-read method on a probe
  or metrics path while draining (documented behavior).
- **B10:** error message texts no longer quote client input (message texts
  are internal).
- **B11:** `422 invalid_request` or `409 inspection_disabled` instead of a
  plain-text `400` for a non-UTF-8 inspection path (experimental routes).
- **`too_many_connections`** joins the `ErrorCode` enum and the OpenAPI enum
  (decision 5); the wire bytes of the accept-loop rejection are unchanged.

### Configuration

- **Console variables renamed (S13, #128):** `KNOTREL_CONSOLE_UPSTREAM` and
  `KNOTREL_CONSOLE_UPSTREAM_TIMEOUT` replace `KNOTREL_UPSTREAM` and
  `KNOTREL_UPSTREAM_TIMEOUT`. The old names are deprecated aliases for 1.x:
  an alias alone is used with a deprecation warning, an alias equal to the
  new name is redundant (warning), and different values refuse to start.
  Console images up to 0.9.x accept only the old names.
- **The server ignores the console namespace:** every `KNOTREL_CONSOLE_*`
  name and the two legacy names are console-owned; the server ignores them
  silently, so one environment file can configure both. Every other unknown
  `KNOTREL_*` name still stops the server.
- `KNOTREL_MODE=source-managed` is a documented, stable alternative spelling
  (B7). No other variable, default or accepted value changed.

### Rust and toolchain

- **Rust:** apart from the approved changes above, API additions only,
  checked by `cargo-semver-checks` against v0.9.0 and by the public API
  snapshot. Under Cargo's rules, moving from 0.9 to 1.0 requires updating
  the version requirement (`knotrel-core = "1"`).
- **Toolchain:** Rust 1.100.0 for the workspace; `knotrel-core` MSRV 1.98.1,
  unchanged.

## Performance qualification

The v1.0.0 campaign ([plan](v1.0.0-qualification-plan.md); decision record
[`results/v1.0.0-qualification/DECISION.md`](https://github.com/knotrel/knotrel-benchmarks/blob/main/results/v1.0.0-qualification/DECISION.md)
in knotrel-benchmarks) measured candidate `0c49b2a` (1.0.0-rc.1) against the
published v0.9.0 on 2026-11-23.

- **Campaign execution: valid.** Part 1 CONFORMING (77.6 of 105 min), block
  Q COMPLETE (27.5 of 30 min). The core rule added B1–B3, B5 and T5.
- **Release qualification: accepted with exceptions.** This is not "all
  gates PASS". No deciding result is REGRESSION or FAIL. Every verdict is
  kept as measured; the maintainer's dispositions are recorded next to them,
  and no v0.9.0 acceptance was inherited.
- **PASS:** A 8 of 9 cells; B1–B3 37/37; B4 deciding 21 of 22; B5 2/2;
  C1–C3 105/105; T5 6/6; R 9 of 11 (one PASS (IMPROVED)); Rmem 20/20
  metrics; M_reg 6/6; feeder Q1, Q2, Q4 and Q5 (Q5 against v0.9.0 in the same
  session: query throughput ×1.07 at 16 clients and ×1.01 at 64).
- **Accepted inconclusive results** (dispositions, verdicts unchanged):
  - A `http_standalone_batch_b256`: **UNRESOLVED**. The primary metric is
    within tolerance; the sampled RSS interval [−7.1%, +22.4%] crosses the
    20% tolerance. No RSS claim for this cell.
  - B4 `metrics-ops` (E3): **INCONCLUSIVE**. In the measured configuration,
    enabling metrics increased batch-operation time by 5.4%; the confidence
    interval [+1.5%, +6.6%] crosses the 6% budget, with upper bound +6.6%.
  - R `core-import` sparse and hub 10k: **INCONCLUSIVE**, neutral medians
    (−1.9%, −0.7%) with wide intervals. No equivalence claim at 10k.
- **Q3, feeder catch-up under query load: FAIL**, accepted as a known limit
  with an operational envelope
  ([feeder under load](../integrations/feeder-under-load.md#v100-qualification-result-and-operational-envelope-2026-11-23)).
  At G100k the catch-up rate fell from 178,095 events/s without queries to
  31,455 (17.7%) with 16 query clients and 16,675 (9.4%) with 64, against
  thresholds of 50% and 25%. Consistent with what was observed in v0.9.0;
  no claim of absence of regression. Its diagnosis (R2) is separate.
- **Not qualified (E6):** the B4 lifecycle `ops` and `events` requirements on
  the compact-bfs hub 10k graph have no equivalent reference. They are
  accepted as unqualified requirements for 1.0, with no performance claim.
- **Disclosures** (reported by rule, not converted): C4 RSS EXCEEDS_BUDGET in
  six cells; B4 `import-high` descriptive REGRESSION (+402%, within the
  candidate build, as in v0.9.0); B4 `ops` sparse 100k descriptive
  INCONCLUSIVE (+19.9%, interval up to +25.1% against 25%).
- Measured on one Apple M3 (16 GB) with the server, PostgreSQL 18.7 and the
  load generator on the same machine. No result is claimed for other
  hardware.

**Transfer to 1.0.0 (maintainer waiver, 2026-11-24).** The measured candidate
carries the version `1.0.0-rc.1`; no release candidate was published. The
release commit differs from it in `crates/`, `Cargo.toml`, `Cargo.lock` and
`rust-toolchain.toml` only by the four version lines, with the same resolved
dependencies and build configuration. The version change alone alters the
`__TEXT,__text` section of the release build, which the qualification plan
requires to be identical; the maintainer waived that requirement for this
step only ([waiver record](v1.0.0-text-identity-waiver.md)). The qualification
above applies to 1.0.0 unchanged, with all its exceptions and limitations.
Binary identity with the measured build is not claimed, and 1.0.0 was not
measured again.
