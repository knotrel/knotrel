# Knotrel v0.9.0 Release Notes — Integration and Contracts

**Status: DRAFT, not released.** Open before release: the release gates
below (including the checks on the final commit) and the maintainer's go for
the tag. The 0.9.6 performance campaign is done: release accepted with
exceptions (see [Performance qualification](#performance-qualification)).
Sections marked *pending* are filled in when the corresponding step is done.

## Scope

v0.9.0 is the last minor before the 1.0 release candidate. It adds a
reference PostgreSQL integration (an external feeder, outside the server),
reserves server admission capacity for feeder requests, fixes the
compatibility policy and stability classes that apply from this release, and
documents a verified deployment with TLS and authentication in front of the
server. Lockstep: `knotrel-core`, `knotrel-server` and the console share the
version 0.9.0 and one tag, `v0.9.0`.

With the default configuration in standalone mode a v0.9.0 server behaves
like v0.8.0. In source-managed mode the admission bound changes (see
Compatibility).

## What changed

**Reference PostgreSQL feeder (roadmap 0.9.1, 0.9.2).**
- `integrations/postgres-feeder/`: an external process that reads two tables
  with logical replication and keeps a source-managed server synchronized.
  Its own Cargo workspace and lockfile; building Knotrel never builds it, and
  it is not published as a crate.
- Guarantees and limits: [design](../integrations/postgresql-feeder.md). No
  lost update between snapshot and stream, progress confirmed to PostgreSQL
  only after Knotrel applied it, full rebuild after every Knotrel restart,
  bounded WAL retention, and **no PostgreSQL transaction atomicity in
  Knotrel**.
- Tested in CI against PostgreSQL 15, 16, 17, 18 and 19, including an upgrade
  from the previous Knotrel release.
- Example with Compose: [`examples/postgres-feeder/`](../../examples/postgres-feeder/).

**Server: reserved admission lanes for feeder requests (0.9.3).**
- In source-managed mode, feeder events, barriers and gap declarations use
  their own permits (`KNOTREL_FEEDER_RESERVED_JOBS`, default 4, from 1 to 64)
  and feeder sessions and heartbeats a control lane of 2 permits. Queries no
  longer starve the feeder: at 64 query clients the feeder's `503` refusals
  went from 188–243 per minute to none in the measured configuration.
- `GET /v1/info` reports `feeder_reserved_jobs`.
- Measurement: [feeder progress under load](../integrations/feeder-under-load.md).

**Contracts toward 1.0 (0.9.4).**
- [Compatibility policy](../compatibility.md) and
  [stability classification](../stability.md), approved by the maintainer on
  2026-11-21, apply from this release.
- CI job `API compatibility`: `cargo-semver-checks` for the Rust crates and
  an OpenAPI comparison against the previous release.

**Verified deployment (0.9.5).**
- [`examples/gateway/`](../../examples/gateway/): nginx in front of the server
  and the console, TLS 1.2/1.3, HTTP Basic with separate operator and feeder
  credentials, server on loopback only; a smoke test runs in CI.
- [Deployment guide](../deployment.md): gateway, and upgrade between minor
  versions (stop, replace the binary, start, rebuild from the source).

**Console 0.9.0.** No change to the UI. The container gets an optional
`KNOTREL_CONSOLE_LISTEN` (default `8080 [::]:8080`, as before), used by the
gateway example to listen on loopback only. Supported server range now
`>=0.8.0 <0.10.0`.

## Compatibility

- **HTTP:** additive only (field `feeder_reserved_jobs` in `GET /v1/info`).
  No route, field or status removed or changed.
- **Admission bound (source-managed mode):** queued plus running jobs are now
  at most `KNOTREL_MAX_PENDING_JOBS` + `KNOTREL_FEEDER_RESERVED_JOBS` + 2
  (default 32 + 4 + 2), against 32 in v0.8.0. Standalone mode is unchanged.
- **New setting:** `KNOTREL_FEEDER_RESERVED_JOBS`, **experimental** (may
  change or be removed in a minor release).
- **Rust:** API additions only, checked by `cargo-semver-checks`. Under
  Cargo's rules for 0.x crates, moving from 0.8 to 0.9 requires updating the
  version requirement (`knotrel-core = "0.9"`).
- **Toolchain:** Rust 1.100.0 for the workspace; `knotrel-core` MSRV 1.98.1,
  unchanged.
- **Console and servers (mandatory check):** the console's browser tests
  (14 tests, Chromium and Firefox) passed against the v0.9.0 candidate server
  and against a server built from tag `v0.8.0`, 14 of 14 on each browser for
  each server. `knotrel.supportedServer` is set to `>=0.8.0 <0.10.0`, exactly
  the minors verified. *To be repeated on the release commit.*

## Declared limitation: Q3 FAIL

**Feeder catch-up under query load does not meet its criterion.** Accepted by
the maintainer on 2026-11-21 as a declared limitation of v0.9.0, limited to
the measured configuration: one Apple M3 with 8 CPUs, macOS 26.5.2, loopback,
PostgreSQL 18.7, graph G100k, the protocol's writer rate and backlog, query
clients with backoff.

| G100k catch-up of a 100,000-change backlog | Required | v0.8.0 | v0.9.0 (0.9.3) | v0.9.0 (0.9.6, release candidate) |
| --- | --- | --- | --- | --- |
| 16 query clients, share of the no-query rate | ≥ 50 % | 16.3 % | 14.7 % | 18.0 % |
| 64 query clients, share of the no-query rate | ≥ 25 % | 2.1 % | 8.9 % | 10.1 % |
| 64 query clients, time to `ready` (Q4, passes) | ≤ 60 s | 25.0 s | 5.5 s | 5.8 s |

The result is FAIL; the thresholds are unchanged. No cause is claimed: host
CPU contention is a hypothesis that was not tested. Freshness under typical
load (Q1), no growing lag (Q2), bounded recovery (Q4) and query cost (Q5: throughput and p99 within the release tolerances of v0.8.0) pass on v0.9.0
in the same measurement, and again in the 0.9.6 campaign on the release
candidate. Follow-up:
[knotrel/knotrel#87](https://github.com/knotrel/knotrel/issues/87): diagnosis
in the 1.0 release-candidate cycle (roadmap R2), fix in v1.2.0 (H2).

## Performance qualification

Two separate statements:
- **Campaign execution: valid.** The 0.9.6 campaign
  ([plan](v0.9.0-qualification-plan.md), protocol frozen in knotrel-benchmarks
  before collection) conformed in attempt 2, in its deciding part (candidate
  `e827b2a` against published v0.7.0, the v0.7.0 qualification-3 method and
  thresholds unchanged) and its descriptive part (against published v0.8.0).
  The feeder-under-load measurement completed. Attempt 1 exhausted its time
  budget because of interactive use of the host; it is kept and not used.
- **Release: accepted with exceptions, for v0.9.0 only** (maintainer
  decision 2026-11-22). This is **not** "all gates PASS" and not a complete
  qualification. Every classification, interval and threshold stands as
  measured; nothing was converted into PASS and nothing was measured again.

**Accepted exceptions (deciding results that are not PASS):**

| Result | v0.7.0 → v0.9.0 | Tolerance | Status |
| --- | --- | --- | --- |
| Core sparse traversal, `compact-bfs` (release cell) | +5.1% [−2.6%, +13.8%] | 10% | INCONCLUSIVE_DISCLOSED |
| HTTP batch size 256 (release cell): timing PASS, sampled RSS | +1.2% [−2.3%, +23.0%] | 20% | UNRESOLVED |
| Metrics overhead, lifecycle batches, sparse 10k | +5.3% [+0.9%, +7.8%] | 6% | INCONCLUSIVE |

| Core flagged import, hub 10k | −3.3% [−17.3%, +20.7%] | 10% | INCONCLUSIVE |

**Not qualified by comparison, accepted for v0.9.0:** lifecycle batches
(`ops`) and feeder events on the `hub` 10k topology. No reference with the
candidate's atomicity exists there; indicative comparisons against
non-atomic references are +10.8% or −3.5% (batches), +5.0% or −5.9%
(events). Roadmap: v1.2.0 (H2).

**Still disclosed:** six RSS-retention cells under churn exceed their budget
(disclosure category, the same six as in v0.7.0; the heap rule passes in
all 15); imports dominated by inactive entries cost about 5× an import of the
effective graph only (+400%, descriptive; +55% against a
capability-equivalent reference, PASS).

**Everything else deciding passed:** 7 of 9 release cells, 58 of 59
lifecycle timing cells, B5, C1–C3, compaction pauses 6/6, 9 of 11 flagged
imports and churn, memory 10/10, concurrency 6/6.

**Against v0.8.0 (descriptive, no verdict):** for the six feeder-event
lifecycle cells the median ratios are between 0.94 and 1.00 (unpaired), and
the six concurrency cells are within their tolerances (throughput −1.3% to
+0.5%, p99 −5.2% to +1.3%). This is limited to these cells on the measured
host.

**Feeder under load on the candidate:** Q1, Q2, Q4 and Q5 pass; Q3 stays FAIL
(see above).

**Not claimed:** v0.9.0 is not claimed to be faster in general than v0.7.0
or v0.8.0. Apple M3, macOS only.

Release commit rule: its `crates/`, `Cargo.toml` and `Cargo.lock` must equal
the candidate's (`main` at `cd803e8`: identical; to be checked again on the
final commit). Summary for users: [performance by
version](../performance-by-version.md). Decision record: knotrel-benchmarks
`results/v0.9.0-qualification/DECISION.md`.

## Review

0.9.1–0.9.5 were reviewed by independent AI review agents before the
release. This is not a human review and does not replace the independent
acceptance review planned for the release candidate. Findings and fixes:

- PostgreSQL feeder ([#96](https://github.com/knotrel/knotrel/pull/96)): no
  heartbeat during the bootstrap (high; an image slower than the lease
  retried forever), a stale-epoch heartbeat answer stopping the feeder,
  missing rollback after a failed snapshot import, generated columns, slot
  ownership by prefix only.
- OpenAPI compatibility check ([#97](https://github.com/knotrel/knotrel/pull/97)):
  `oneOf`/`anyOf` members not compared (high), response headers, `null`
  alternatives, and the experimental marker in the new version silencing
  breaks.
- Gateway example ([#92](https://github.com/knotrel/knotrel/pull/92)): CA key
  mounted into the gateway, console reachable from other containers on the
  network, a TLS 1.1 check that could not fail.
- Admission lanes (0.9.3): no defect found.
