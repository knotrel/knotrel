# Knotrel v0.8.0 Release Notes — Operational Console

**Status: DRAFT, unreleased. Performance qualification pending; release gates
outstanding.** Nothing below is published until the gates at the end are
closed.

## Scope

v0.8.0 adds a browser console for operating one server and the read-only
server routes it needs to browse a graph. It is the first release in
lockstep: `knotrel-core`, `knotrel-server` and the console share the version
0.8.0 and one tag, `v0.8.0`.

Everything new on the server is **opt-in**: with the default configuration a
v0.8.0 server behaves like v0.7.0.

## What changed

**Server: read-only inspection routes (opt-in, `KNOTREL_INSPECTION=true`).**
- `GET /v1/nodes`, `GET /v1/nodes/{node}`, `GET /v1/nodes/{node}/edges` and
  `GET /v1/edges` list nodes and edges with cursor paging and state filters,
  without knowing IDs in advance.
- Pages are bounded: at most 1000 items and a scan budget of 10 000 entries
  per page, independent of graph size. Cursors are positions, never expire,
  and pages are not a snapshot (elements present for the whole traversal
  appear exactly once).
- Available in standalone and source-managed modes; never mutating.
  Incident and edge listing need the `compact-bfs` engine; `ett` and `hdt`
  list nodes only.
- New error codes `inspection_disabled` (409), `inspection_unsupported`
  (409) and `invalid_cursor` (422); `GET /v1/info` reports
  `"inspection": true` when enabled; new job kind `inspect` in metrics.
- Contract: [HTTP API, Inspection](../http-api.md#inspection-opt-in) and
  `docs/openapi.yaml`.

**Core: neighbor listing.**
- `Graph::degree`, `Graph::neighbors_after` (cursor paging) and the opt-in
  `Graph::enable_neighbor_listing`, with `IncidenceError`.
- `LifecycleGraph::degree` and `LifecycleGraph::incident_after`.
- `ConnectivityGraph::contains_node` is now public;
  `ConnectivityGraph::as_compact` and
  `ConnectivityGraph::enable_neighbor_listing` are new.
- All additions; no existing API changed.

**Console 0.8.0 (new artifact).**
- Browser for nodes and edges with a detail pane, neighbors and a
  connectivity check; workbench for queries and validated batches with
  history and saved requests; performance from `/metrics`; overview; and
  synchronization for source-managed servers. Dark and light themes.
- Distributed as the container image `ghcr.io/knotrel/knotrel-console:0.8.0`
  and a reproducible static archive attached to this release. The Rust
  binary embeds no console assets and Cargo never needs Node.js.
- No authentication: access control belongs to the gateway in front of it.
  The container forwards only an allowlist of read and operation routes;
  feeder routes are never forwarded.
- Guide: [docs/console.md](../console.md).

**Documentation and process.**
- `docs/openapi.yaml` now documents fields and headers the server already
  returned (`/v1/info` mode and instance, `/v1/stats` source-managed fields,
  readiness labels, version headers); `info.version` is 0.8.0.
- Lockstep versioning: one version and one tag for core, server and console
  (`CONTRIBUTING.md`).

**Dependencies.** `fixedbitset` 0.5.7 → 0.5.9 (re-applied after v0.7.0, as
announced in its release notes).

## Compatibility

- **HTTP:** no existing route, field or status changed. The inspection
  routes exist only when enabled; without the flag they answer 409
  `inspection_disabled`.
- **Rust:** API additions only. Under Cargo's rules for 0.x crates, moving
  from 0.7 to 0.8 still requires updating the version requirement
  (`knotrel-core = "0.8"`).
- **Toolchain:** Rust 1.100.0 for the workspace; `knotrel-core` MSRV 1.98.1,
  unchanged.
- **Console and servers:** use the console with the server of the same
  version. With a v0.7 server every page works except the Browser (verified
  against a server built from tag `v0.7.0`).

## Costs and resource limits

With inspection **off** (default) the server keeps no extra state; the only
change on the node-registration path is a check of an empty optional field.

With inspection **on**, a targeted cost check (not a release qualification;
protocol and criteria fixed before measuring;
[results](../console-inspection-costs.md)) on 500 000 nodes and 1 500 000
edges found:
- page cost: client p95 0.47 ms, server p95 ≤ 0.5 ms;
- concurrent worst-case browsing raised mutation p95 from 0.081 to 0.453 ms
  and query p95 from 0.084 to 0.144 ms;
- node-creating throughput 95–98% of inspection off;
- memory: an ordered node index (measured 5.6–11 bytes per node) plus, on
  plain `compact-bfs`, 8 bytes per node; documented as "up to about 20 bytes
  per node".

One machine, one run per measurement, loopback only.
