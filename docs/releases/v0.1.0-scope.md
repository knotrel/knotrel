# v0.1.0 public-preview scope

## Audit and decision

Feature 0.1.1 inventories and freezes the release boundary; it does not add a
runtime capability. Audited on 2026-10-13 against
`95574219161244ab572c125ff2da5228be4cc897`, with an initially clean working tree.
The workspace contains `knotrel-core` (library) and `knotrel-server` (library and
binary), both at 0.1.0, edition 2024, with `publish = false`.

The release is a synchronous Rust library and an **experimental, volatile,
single-graph HTTP service for localhost or trusted, access-controlled use**.
Stopping the process loses the graph. Untrusted exposure is unsupported and
would make authentication, authorization and abuse tests release blockers.

Existing batches and statistics are retained as compatibility scope, even
though new batch development is not required by the roadmap's preview. Do not
remove them or replace their continue-after-error semantics with the future
durable committed-prefix model. No new HTTP import or batch design is included.

| Liveness | `/health` returns `{"status":"ok"}` without the graph lock; does not establish readiness or worker availability | [Router](../../crates/knotrel-server/src/lib.rs), `preview_health_and_configured_state_ownership` in [HTTP tests](../../crates/knotrel-server/tests/http.rs) |

| Failure handling | Graph-capacity violations leave state unchanged; busy work returns 503; a panicked worker makes graph work unavailable; admitted work can outlive a disconnected requester | [Service](../../crates/knotrel-server/src/service.rs) unit tests, [HTTP error table](../http-api.md) |
| Lifecycle today | Ctrl-C and Unix SIGTERM drain active work; no readiness route or bounded drain deadline yet | [Binary](../../crates/knotrel-server/src/main.rs), [configuration-failure test](../../crates/knotrel-server/tests/startup.rs) |

Core algorithms remain synchronous and independent of HTTP. The core currently
depends on `rustc-hash`, `nohash-hasher`, `fixedbitset` and `tinyvec`; it is **not
dependency-free**. See its [manifest](../../crates/knotrel-core/Cargo.toml).
No dependencies, algorithms, transport behavior or defaults change in this task.

Cardinality caps do not bound retained allocation, RSS or total network memory.
Graph admission happens after body parsing, so it does not bound concurrently
buffered bodies or connections. Allocation failure is not a recoverable graph
error. These limitations are accepted only within the restricted preview trust
boundary, not as a resource-safety guarantee for untrusted deployment.

## Runtime and distribution matrix

Rust **1.98.1** is the pinned build/test toolchain and declared `rust-version`.
No lower MSRV is claimed; no separate historical-toolchain compatibility promise
is made.

The [CI run for audited HEAD](https://github.com/knotrel/knotrel/actions/runs/38412646841)
passed all three native build/release-build/test jobs:

| Platform | Verified source-build/test target | Distribution promise |
| --- | --- | --- |
| Linux | `ubuntu-latest` native GitHub-hosted runner | No released binary/container verified yet |
| Windows | `windows-latest` native GitHub-hosted runner | No released binary verified yet |
| macOS | `macos-latest` native GitHub-hosted runner; local macOS arm64 validation subject to the limitations below | No released binary verified yet |

Support is limited to these native source-build/test environments. CI does not
pin architecture or exercise cross-compilation; do not infer an architecture
matrix from OS labels. Other architectures, packaged artifacts and production
service operation outside the development environment are not certified.
Release-mode lifecycle smoke tests on every claimed deployment target remain a
0.1.6 gate, not a promise inferred from successful compilation.

equivalent to release acceptance, and this inventory does not check later
features automatically.

| 0.1.3 safe boundary | Loopback default, strict content type/JSON checks, body/batch caps, optional graph caps | Complete trust/proxy guidance and default log/error disclosure review; do not treat network isolation alone as authorization |
| 0.1.4 health / lifecycle | Liveness, startup configuration validation, Ctrl-C / Unix SIGTERM handling | Add readiness states, bounded draining and release-mode startup/mutate/query/shutdown/restart-empty/failed-bind smoke tests |
| 0.1.5 library adoption | Rustdoc examples, ordered constructor and oracle tests, architecture notes | Runnable standalone examples, publication/API metadata audit and evidence-grounded engine guidance |
| 0.1.6 release validation | Three-OS CI build/test, formatting, Clippy, Rustdoc and coverage workflows | Artifact smoke matrix, clean publication/package/license audit, release notes and compatibility policy; publishing/tagging require approval |

Known pre-tag blockers are the outstanding work in this table and unavailable
validation gates below. They have assigned roadmap owners rather than unresolved
scope decisions. Default unlimited cardinality, experimental ETT/HDT and
volatile state are explicit preview limitations, not undocumented promises.
The Elastic-2.0 repository license must be reflected correctly in any package
metadata before publication; this inventory makes no licensing changes.

Persistence/WAL/snapshots/recovery and bounded HTTP import belong to v0.2.0.
New durable batches, metrics and measured concurrency optimization belong to
v0.3.0. Multi-graph, HA, distributed storage, stable pre-1.0 APIs, cross-request
transactions and exactly-once delivery are not preview guarantees.

## Execution, tests and performance protection

1. Audit the clean checkout and existing tests before changing anything.
2. Add scope-level tests for health and configured router state ownership for all
   three HTTP engines, without duplicating existing algorithm/contract tests.
3. Freeze this note, link it from the README and update only verified roadmap
   sub-tasks. Keep release acceptance pending if a required gate cannot run.
4. Run formatting, warning-denied Clippy/Rustdoc, workspace tests and per-crate
   `codectl` (`--artifact library` for core, `--artifact service` for server).
5. Confirm production sources, manifests and lockfiles are unchanged. Establish
   diagnostic before/after measurements using the existing sibling harness.

The performance baseline uses benchmark checkout
`aa2412dfa50e7a71439fc8374ce81055e220aad0`, initially clean, and the audited core.
Run from the sibling benchmark workspace, build once with
`cargo build --release --locked`, then use the same executable for both phases:

```sh
target/release/knotrel-benchmarks \
  --engine compact-bfs,ett-scan,hdt \
  --workload chain-split-rejoin-v1 \
  --nodes 256 --rounds 200 --seed 42 --warmup 2 --repetitions 5
```

Repeat in three independent processes per phase for each of
`chain-split-rejoin-v1`, `cycle-alternatives-v1` and `dense-bridge-churn-v1`.
Keep raw JSON, both revisions/dirty states, compiler/OS/architecture, trace
fingerprints and executable SHA-256 with the evidence. The harness checks
expected results outside timed calls. Compare setup, workload wall time and
operation p95/p99 distributions; do not choose only the fastest repetition.
These are embedded kernel measurements, **not HTTP throughput, RSS or lifecycle
latency** and not a new performance SLO.

For this documentation/test-only change, unchanged production inputs and an
identical benchmark executable are the regression protection; timing variation
of identical code must not be labeled a speedup or code regression. A future
runtime change must agree workloads and regression budgets before editing,
collect an unchanged baseline, include HTTP/mixed-load and process memory when
relevant, and investigate repeated effects separately from measurement noise.
