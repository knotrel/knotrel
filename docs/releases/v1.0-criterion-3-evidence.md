## 1. Randomized soak

### 1.1 Where it lives and what it does

[`crates/knotrel-server/tests/soak.rs`](../../crates/knotrel-server/tests/soak.rs)
is a server integration test. It drives real `knotrel-server` child processes
(the binary Cargo builds for the test, configured only through `KNOTREL_*`
variables) over loopback HTTP, like
[`e2e_rebuild.rs`](../../crates/knotrel-server/tests/e2e_rebuild.rs), and
reuses the raw HTTP client of `tests/common/feeder.rs`. It needs no Node.js,
no external service and no feature flag.

One seeded SplitMix64 generator makes every decision. Requests are strictly
sequential, so a run is a deterministic function of its seed and settings;
wall-clock time only bounds the run and the deliberate lease expiry.

**Authoritative source.** An append-only log of changes that are valid for the
source (`add_node`, `link`, `cut`, `progress`, and with lifecycle support
`set_node_active`, `set_edge_enabled`, `remove_node`) over a fixed universe of
12 node IDs, including `0`, IDs above 2^53 and `u64::MAX`. Change *k* has
position `p<k>` and event ID `ev<k>`. `KNOTREL_MAX_NODES` equals the universe
and `KNOTREL_MAX_EDGES` is 10, so the source runs at capacity regularly. The
source can reset its epoch.

**Server incarnations.** At start and at each restart (an abrupt kill:
`SIGKILL` on Unix, `TerminateProcess` on Windows) the soak picks, from the
seed: source-managed (80 %) or standalone mode; the engine (`compact-bfs`,
`ett` or `hdt`; only `compact-bfs` with lifecycle support); and
`KNOTREL_DEDUP_WINDOW_SIZE` among 1, 2, 3, 5, 8 and 64. Inspection is always
on (it is the verification channel). Lifecycle support is fixed per run.

**Source-managed actions** (weighted by state, every action always possible so
that off-policy requests are exercised):

| Area | Actions |
| --- | --- |
| Sessions | register, heartbeat, epoch bump, takeover by a second session ID, stale (lower-epoch) registration, deliberate lease expiry (one-second lease, wait 1.25 s), recovery by re-registering the same epoch (still fenced for barriers) or a higher one |
| Imports | `create_only` of a source snapshot at the head or up to 7 changes behind it (a backlog to catch up), with lifecycle flags as objects; `replace` with the current `ETag` (rebuild from source), with a stale `If-Match`, or on an uninitialized graph; `create_only` on an initialized graph |
| Events | the next 1–6 source changes, optionally preceded by exact retries of retained events; duplicate-only requests; evicted duplicates and sequence 0 after events were applied; sequence gaps (first or later event); a domain failure (self-loop, `unknown_node`, `unknown_edge`, node and edge limits) after a valid prefix, followed by later events, and the exact resend of a failed request; conflicting duplicates (other event ID, other operation or flag, other endpoints, other source position, retained event ID at a new sequence); predecessor mismatch (sequence or position); stale generation; stale session or epoch; other `source_id`; source epoch reset; stale instance ID after a restart; lifecycle events while lifecycle support is off |
| Barriers | exact, premature, superseded, other position, stale epoch |
| Other | gap declaration; `connected`, `node_state`, `edge_state` through `/v1/operations` and query-only `/v1/batch`; direct mutations through `/v1/operations` and mixed `/v1/batch` (409); restarts |

**Standalone actions:** single mutations and queries, continue-on-error
`/v1/batch` with up to 16 mixed operations (including self-loops, limits and
unknown nodes), feeder requests (409 `mode_conflict`), restarts (volatile
state is lost).

### 1.2 Reference model and checks

The model in `soak.rs` (`Topology`, `Feed`, `Model`) is written from the
documents, not from the server code: registered topology with flags and
limit precedence (`docs/http-api.md`, "Single operations", "Node and edge
lifecycle"); sessions, lease, fencing and `last_expired_epoch`
(`docs/http-api.md`, barrier and recovery fencing); the event pipeline and the
§9.3 failure matrix; the barrier decision table B1–B9; atomic publication
(§8.2); the query gate of source-managed mode. Where the documents leave the
order of two whole-request checks open, the soak never injects both at once.

After **every** step the soak compares:

- the response of the step: HTTP status and every contract field (`result`,
  `code`, frontier, `state_version`, `events_applied`, partial-failure
  indices and inner `error.code`, duplicate `historical_outcome`, barrier and
  gap status, session status, import generation), and every per-item result
  of a batch;
- `GET /v1/stats`: counts (with lifecycle support the active, enabled and
  effective counts), `state_version`, `generation`, `sync_status`,
  `source_position` and the `ETag`;
- `GET /ready` status and body (precedence uninitialized, desynchronized,
  stale, catching up, ready);
- `GET /v1/nodes` (every registered node with `active` and degree) and, on
  `compact-bfs`, `GET /v1/edges` (every edge with `enabled` and `effective`);
- one query batch with `connected` for every pair of the universe plus an
  unregistered ID (and `node_state` with lifecycle support): 91 or 104
  queries, which checks every engine's connectivity answer;
- that the model, after applying the delivered events, equals the source
  snapshot at `base + applied_delivery_sequence` (convergence to the source
  after every rebuild and catch-up).

```bash

```

```bash
KNOTREL_SOAK_SEED=0xa11ce KNOTREL_SOAK_STEPS=200000 KNOTREL_SOAK_SECONDS=3600 KNOTREL_SOAK_LIFECYCLE=on cargo test --release -p knotrel-server --test soak soak_long -- --ignored --nocapture
```

Other settings: `KNOTREL_SOAK_LEASE_EXPIRIES` (default 4, about 1.25 s each),
`KNOTREL_SOAK_TRACE=1` (print every step). Without
`KNOTREL_SOAK_LIFECYCLE` the seed chooses. A run prints its seed first and a
coverage summary (count per action and per response code) at the end. A
failure prints the seed, step, server configuration, the exact command that
reproduces it (same seed, `KNOTREL_SOAK_STEPS` set to the failing step), the
last 40 steps, the expected and actual responses, the model state and the
server's stderr.

## 2. Findings

### D1 (defect): sequence 0 before the first applied event panics the graph worker

- **Found by:** the soak (then behind a gate for known defects, removed
  after the fix). Minimal seed:

  ```bash
  KNOTREL_SOAK_SEED=0x2 KNOTREL_SOAK_STEPS=8 KNOTREL_SOAK_LIFECYCLE=off KNOTREL_SOAK_LEASE_EXPIRIES=0 cargo test -p knotrel-server --test soak soak_long -- --ignored --nocapture
  ```

  Deterministic reproduction, now a regression test that runs by default:
  `regression_d1_sequence_zero_at_generation_start` in `soak.rs` (register,
  `create_only` import, one event with `delivery_sequence: 0`).
- **Condition:** source-managed mode, valid session, lease, generation and
  source lineage, and `applied_delivery_sequence == 0` (right after any
  import, before the first event of the generation is applied); the first
  event that reaches the sequence check has `delivery_sequence: 0`.
- **Expected** (`docs/http-api.md`, invariant 7: wrapped sequences `D = 0`
  are rejected with 409 `unverifiable_duplicate` without state mutation;
  §9.2, evicted history boundary): 409 `unverifiable_duplicate`, state
  unchanged.
- **Actual:** `DedupWindow::check_sequence` returns `Future` when the applied
  sequence is 0 and `apply_events` treats that as `unreachable!()`
  (`crates/knotrel-server/src/service.rs`, the `DedupLookup::Future` arm).
  The worker panics; the request gets 503 `unavailable` and the panic guard
  marks the server permanently unavailable: every graph request and `/ready`
  answer 503 `unavailable` until the process is restarted and rebuilt from
  the source.
- **Impact:** one request from the (trusted) feeder, for example a feeder bug
  that sends 0-based sequences, takes the server out of service. Within the
  trust model this is an availability defect, not a security boundary
  violation; it is relevant to the threat model (criterion 7).
- **Fixed** in knotrel/knotrel#104 (maintainer approval 2026-11-22,
  merged on `main` as `0fe35f6`). `DedupWindow::check_sequence` now
  classifies every input totally (sequence 0 is `Evicted`; `Future` exactly
  when the sequence is above the applied one), and `apply_events` matches on
  that one classification, so no feeder input reaches an `unreachable!()`
  arm. Wire behavior, `docs/openapi.yaml` and the documents are unchanged: the
  fix makes the server match invariant 7. Regression tests: `events.rs`
  `test_29` (sequence 0 single and multi-event, `u64::MAX` and a gap right
  after an import, after a `create_only` and after a `replace` import;
  frontier, readiness and later events checked) and
  `regression_d1_sequence_zero_at_generation_start` in `soak.rs`. The soak
  now sends sequence 0 in every state. The fix is changed release code for
  the v1.0 campaign.

### F2 (documentation): query-only batches while unsynchronized

**Closed.** Fixed in the contract freeze documentation fixes
(knotrel/knotrel#115, `a6624c1`): the §2.3 row for a query-only `/v1/batch`
now reads "200 with one `uninitialized`, `loading` or `desynchronized` error
result per operation", which matches the server, OpenAPI and the soak. The
original finding follows.

[Integration contract §2.3](../integration-contract.md#23-mode-admission--route-enforcement-matrix)
says a query-only `/v1/batch` in source-managed mode returns "503 if
uninitialized/loading". The server returns **200** with a per-item error
(`uninitialized`, `loading` or `desynchronized`) for every operation, which
matches `docs/openapi.yaml` (no 503 refusal for `/v1/batch`) and is what the
soak expects. Single `/v1/operations` queries do return 503. The §2.3 row
should be corrected in the contract freeze review (criterion 1); this is
outside §9.

## 3. Traceability of integration contract §9

**Method.** §9 contains no RFC 2119 keywords ("MUST" does not occur in the
document). Every normative statement of §9 was therefore taken as a
requirement: server guarantees stated as facts ("is rejected", "returns",
"never"), table rows of the §9.3 failure matrix, and the explicit obligations
("must", "forbidden"). Each was mapped to tests by reading the test names and
their asserted codes; the citations already in §9 were checked the same way.
"Soak" means the requirement is checked by `soak.rs` after every relevant
step.

Status: **Covered** (a test asserts it); **Partial** (only part, or only
structurally); **Uncovered**; **Feeder** (an obligation of the feeder that the
server cannot enforce; listed with what tests the reference feeder).
