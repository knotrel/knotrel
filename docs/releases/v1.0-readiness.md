# v1.0 readiness assessment (v0.6.0 increment 0.6.6)

**Status:** assessment for maintainer review, written on the v0.6.0 candidate;
state updated after v0.7.0 and v0.8.0 on 2026-11-21 (see
[State after v0.8.0](#state-after-v080) and
[State during v0.9.0](#state-during-v090); the checklist keeps its v0.6.0
state column, and no verification was repeated for the update). It states
what the evidence shows and what each gate requires. It
promises nothing beyond that evidence; no item below is accepted until the
maintainer accepts it.

**Path:** v0.8.0 → **v0.9.0** → **v1.0.0-rc** → **v1.0.0**, each step subject
to its stability gates. v0.7.0 closed the graph-lock bottleneck for read-heavy
work measured in v0.6.0 (maintainer decision B, 2026-11-16); v0.8.0 added the
console. v0.9.0 addresses the integration and reliability gaps (criteria 3,
4, 6 and 10, with groundwork for 1 and 2; see the
[roadmap](../../ROADMAP.md#v090--integration--reliability)). Other gaps close
inside the release-candidate cycle. ETT/HDT lifecycle support, local
persistence and multi-graph are **not** v1.0 prerequisites.

Legend: **Met** (evidence exists and is current), **Partial** (evidence exists
but does not cover the claim), **Gap** (missing).

### Declared limitations carried by v0.9.0

- **Q3, feeder catch-up under query load: FAIL**, accepted by the maintainer
  on 2026-11-21 as a declared limitation, limited to the measured
  configuration (one Apple M3, 8 CPUs, loopback, PostgreSQL 18.7, G100k, the
  protocol's rates). Catch-up of a backlog reaches 14.7 % of the no-query rate
  with 16 query clients and 8.9 % with 64 (required 50 % and 25 %); measured
  again on the release candidate in 0.9.6: 18.0 % and 10.1 %, still FAIL. Thresholds
  unchanged; no cause is claimed (CPU contention is a hypothesis that was not
  tested). Follow-up [#87](https://github.com/knotrel/knotrel/issues/87).

## Concrete security gaps within the trust model

These do not require native authentication; they are gaps in the supported
model itself:

1. **Import memory amplification.** In v0.5.0 an HTTP import's parse working
   set was about 10–13 times the body (87–106 MiB for 8.3–9.9 MiB bodies), so
   the default 64 MiB body limit allowed several hundred MiB of transient heap
   from one request. v0.6.0's streaming parse reduces the measured transient
   to about the body plus the graph being built (see the v0.6.0 release
   notes); the deployment guidance must size memory for
   `old graph + body + new graph` and say so.
2. **Lock-holding work per request.** A batch of up to 1024 `connected`
   operations runs up to 1024 BFS traversals under the graph lock, and a
   lifecycle removal can trigger a whole-graph rebuild under the lock. Since
   v0.7.0 query-only batches share the lock, so they no longer delay each
   other, but they still delay every mutation, feeder event and import
   publication, and a rebuild still blocks everything. Any client inside the
   trust boundary can delay others for that long; the
   request timeout bounds the caller's wait, not the worker. Gate: document
   per-request worst-case lock time for the supported envelope and consider a
   configurable batch ceiling.
3. **Feeder takeover is unauthenticated by design.** Session fencing protects
   against stale feeders, not against a hostile client in the boundary. Keep
   it documented as such; any untrusted exposure needs gateway authentication.
4. **`SECURITY.md` is stale** (supported-versions table, missing contact
   address).

## Experimental engines

If `ett` and `hdt` stay exposed in 1.0 they must be documented as
**experimental** with these guarantees only: exact connectivity results under
the same contracts as `compact-bfs` (oracle-tested), no lifecycle support
(rejected at construction and startup), no performance or memory envelope
(HDT retained storage has no established practical steady state), and no
stability promise for their configuration names beyond the deprecation
policy. Alternatively they are removed from the server's supported
configuration before 1.0; either is a maintainer decision.

## v0.7.0

Planned for the measured concurrency gap only (criterion 4 and M5): v0.6.0's
contention evaluation shows that the single graph lock serializes BFS queries
and dominates read-heavy latency at four or more clients. v0.7.0 designs the
minimal change that preserves every service invariant; no mechanism is
prescribed in advance. A batch ceiling setting (criterion 4, gap 2) may join
it if the envelope work shows it is needed. v0.7.0 also evaluates measured
performance candidates (ROADMAP 0.7.4) aimed at v0.6.0 non-PASS results:
- the flagged-import parse cost;
- allocator retention in RSS;
- BFS layout.

Each is adopted only with qualification evidence. Other gaps stay in the rc
cycle.

**Status (2026-11-20):** the shared read lock (0.7.4a) and `sonic-rs` import
parsing (0.7.4b) are implemented, with the catalog tombstone handling.
Qualification 3 (attempt q3-3, conforming) was **accepted with exceptions**
for v0.7.0 only. That is not "all gates PASS".
- **Criterion 4 (concurrency) gains evidence.** Read-heavy throughput
  grows with clients: 2.1× v0.6.0 with 4 clients at 10k nodes, and 4.5–5.2×
  for queries during imports or feeder events at 100k nodes, with lower
  p99. Write-heavy and mixed workloads are unchanged within tolerance.
- **The v0.6.0 C3 heap-growth failures are resolved** (15/15 PASS).
- **Disposed, not resolved:**
  - three INCONCLUSIVE results accepted by the maintainer;
  - lifecycle batches and feeder events on `hub` 10k, not qualified by
    comparison, under a maintainer exception;
  - six C4 RSS cells (disclosure category);
  - the descriptive `import-high` overhead.

  For criterion 5 they count as disposed for v0.7.0 only. They are not
  precedents for v1.0.0-rc.
