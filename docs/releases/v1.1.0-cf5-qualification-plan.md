may start before the maintainer approves this plan (section 14).** Roadmap
item CF5; design in [ADR 0014](../architecture/0014-cluster-forest-backend.md).

changed. No measurement was taken.
Revision 5 (2026-11-24): the maintainer rejected the uniform 1 ms

(section 6.1), estimated from a calibration of the clock and of each
harness's overhead, with its scope (not V1, L2, S3) and its exclusions
stated. Margins, classes, cells and every performance threshold are
unchanged. The calibration measured the instrument only: it took no
cluster-forest observation.

## 1. Purpose

CF5 measures the experimental `cluster-forest` engine against `compact-bfs`,
`ett` and `hdt` under the same semantics, workloads, binary and machine, and
checks that the v1.1.0 changes did not regress the existing engines against
v1.0.0. Every cell is classified under rules fixed here, before any data
exists. The results are the evidence for CF6 (section 12); CF5 itself
changes nothing.

Questions:

1. On which core workloads is `cluster-forest` faster, equivalent or slower
   than each existing engine, for updates, queries and construction?
2. How do its steady and peak memory compare?
3. Does it change end-to-end throughput, latency and feeder freshness, with
   and without lifecycle support?
4. Did CF2–CF4 change the existing engines' performance against v1.0.0?
5. How does `cluster-forest` compare with the **released** default
   (`compact-bfs` in v1.0.0)?

## 2. Candidate, builds and machine

- **Candidate:** the `main` commit containing CF2–CF4 (PR #150), its SHA
  written into the campaign record before the first observation. The
  release code (`crates/`) must not change during the campaign.
- **Baseline:** the v1.0.0 release (tag `v1.0.0`), built from source with
  the same toolchain and flags, for blocks V1–V3.
- One binary per harness and version, release profile, toolchain 1.100.0;
  within a version, every engine is in the same binary and differs only by
  `EngineConfig`.
- `knotrel-benchmarks` pins `knotrel-core`/`knotrel-server` to the
  candidate SHA (and, for V blocks, a second build pinned to `v1.0.0`),
  with `Cargo.lock` hashes recorded.
- **Engine path:** in the core blocks every engine runs through
  `ConnectivityGraph` (harness kinds `connectivity-*`), the product API and
  the only public path of `cluster-forest`, so the engines share one code
  path and differ only by `EngineConfig`.
- The feeder load tool (`integrations/postgres-feeder/examples/load.rs`) is
  built from the candidate source; its `LOAD_ENGINE` variable (added for
  CF5, default `compact-bfs`) selects the engine of the local server and is
  recorded in every observation.
- One dedicated host for the whole campaign, recorded (CPU model, cores,
  frequency policy, memory, OS and kernel), nothing else running.

## 3. Engines and scenario selection

Engines: `compact-bfs` (CB), `ett` (ETT), `hdt` (HDT), `cluster-forest`
(CF). A comparison is always CF against one reference engine, or (V blocks)
the candidate against v1.0.0 for the same engine.

**Selection by representativeness.** Scenarios are taken from the existing
qualification matrices (the v1.0.0 plan's A, B4, C, R, Rmem, M_reg and Q
blocks, and the eight `knotrel-benchmarks` workload families, which cover
sparse, ring, hub, component and dense graphs and the feeder workloads the
roadmap names), plus the published staged protocol of the reference paper
(K2). Margins are the existing tolerances. Nothing is chosen or tuned from
observed results (section 13).

## 5. Method

Timed blocks (K1–K3, K2x, L1, L3, S1, V1–V3) use the paired method of
the v1.0.0 plan (§5.1, option (a) of §5.3):

- **Pairs:** one observation of each arm, each in a fresh process (server
  blocks: a fresh server), order within the pair balanced 12/12 by a frozen
  seeded schedule; pairs interleaved across cells.
- **Fixed n = 24 pairs per cell**, two warmup pairs discarded, no interim
  analysis, no extension; the analyzer runs once, after all pairs.
- **Interval:** distribution-free interval of the median of the 24 paired
  log ratios `ln(CF / reference)` (throughput: `ln(reference / CF)`; V1, V2:
  `ln(candidate / v1.0.0)`): `[r(7), r(18)]`.
- K4 and L4 are deterministic: one run per arm and cell. L2 follows the
  v1.0.0 C rules; S3 follows the feeder protocol (3 observations per cell).
- **Seeds:** workload seeds fixed per cell in the matrix file; the order
  seed drawn once and written into the record before the first observation.

**Correctness gate.** Every core observation checks its answers against
the workload's independent oracle and that every `link` and `cut` reports a
change; every arm checks that the tool ran the expected engine; arms of the
same cell must run the same inputs (edge or trace fingerprint); K4's graph
must also be its K2 cell's (same edge fingerprint); K4's
high-water mark must be exact; every server observation checks
`errors == 0`; L1 checks its answers against the CB plain arm. Some tools
emit no fingerprint, so the same-input check takes these forms: L3 churn
cells compare operation counts; L3 import cells and the server cells (S1,
V2 and V3 M_reg) run identical seeded argv that differ only in the engine,
and their tools generate the inputs without the engine. For S1, V2 and V3 the
engine checked is the one the probe started the server with. For S3 it is the
engine the server reports in `knotrel_build_info`. A failed
check, a non-zero exit or unparsable output is a **FAIL** of the campaign:
CF5 stops, the defect returns to CF3, and a new candidate is needed. A
timeout or a missing executable is an infrastructure failure: the
observation is retried once, then the campaign stops.

**Tier-1 correctness smoke.** Before any measured pair, every distinct arm
runs once (core observations with `--verify true`: an untimed check of the
whole partition that also catches false "connected" answers, which the
protocol's queries rarely probe); deterministic arms run twice. The smoke's
time counts toward the cap.

**What is recorded.** The record, written before the first observation,
holds the matrix hash, the tool map, the SHA-256 of every executable, the
checkout SHAs (candidate, baseline, benchmarks) and lockfile hashes, the
host description and the order seed, which is **derived** from the matrix
hash and the candidate SHA, so it cannot be chosen. Every observation
keeps its full selected output object (report-only metrics included), the
hash of its standard output and its standard-error tail; a failed
observation is recorded too. Host snapshots (load, swap, thermal state)
are taken before and after each block.

## 6. Confidence level: rationale

- **Per-cell level.** `[r(7), r(18)]` at n = 24 covers the median with
  probability 1 − 2·P(Bin(24, ½) ≤ 6) = **97.73 %**, distribution-free,
  assuming independent pairs from a continuous distribution. Each bound is
  a one-sided 98.87 % bound, so the EQUIVALENT class (both bounds inside the
  margin) is a two-one-sided-tests decision with error at most 1.13 % per
  side.
- **Why this level.** It is the v1.0.0 level, so results and tooling are
  comparable across releases (V blocks compare with v1.0.0 directly), and
  the fixed n removes optional stopping, so the stated coverage is the real
  one. A higher level at the same n (`[r(6), r(19)]`, 99.34 %) widens every
  interval and turns more cells INCONCLUSIVE; a higher n multiplies the
  budget. Option offered for approval: keep 97.73 % (recommended) or raise
  to 99.34 % at n = 24.
- **Multiplicity.** With about 230 interval comparisons, about 2.3 % of
  intervals are expected to miss their median by chance alone (around five
  in the campaign). No family-wise correction is applied, because it would
  require n far beyond the budget. Instead the CF6 criteria (section 12)
  never rest on a single cell: they use whole families and sizes, and an
  isolated FASTER or SLOWER cell within an otherwise different family is
  reported as such, not as a finding. No cell is rerun because of its
  result.
- **What the level does not cover.** Host drift between blocks, harness
  bias common to both arms, and workloads outside the matrix.

### 6.1 Measurement limit (TIMER_LIMITED)

**Scope.** This rule applies to the time metrics (margin kinds time and
tail) of the paired cells classified by `analyze_cf5.py`: K1, K2, K2x, K3,
L1, L3, S1, V2 and V3. It does not apply to the following, which keep their
own protocols as declared in section 4:

- **V1** runs the frozen v1.0.0 experiment A analysis (`analyze_v100q_a.py`,
  rule set v0.4.0) unchanged. Its own treatment of the timer is decision
  G3a-1: `link_p99_ns` and `cut_p99_ns` of the four core cells are
  REPORT_ONLY, because their medians are within two ticks. Every other V1
  metric is gated without a timer rule, as in v1.0.0. V1 therefore never
  produces TIMER_LIMITED. It can produce PASS for a metric that this section
  would mark TIMER_LIMITED (for example a `workload_wall_ns` with per-operation
  timing inside). This is a declared difference between protocols, kept for
  comparability with v1.0.0 (section 14, item 9).
- **L2** runs only the C rules (sustained resources: vertex bound, logical
  counts, heap and RSS growth). These rules contain no time metric. The 1 ms
  floor of `analyze_lifecycle_qualification.py` belongs to its B1–B4 timing
  rules, which CF5 does not run.
- **S3** keeps the feeder protocol: absolute Q1–Q4 thresholds on 3
  observations, and Q5-style ratios of medians (≥ 90 % `query_rps`,
  ≤ 125 % `query_p99_ms`). The load tool times each request with `Instant`
  (no millisecond rounding), through an async HTTP client. S3 has no
  TIMER_LIMITED class and no interval to widen. Its p99 values are in
  milliseconds, while one request interval has a clock limit of about 58 ns.
  No exception is made: the rule has no object there.
- K4 and L4 are memory comparisons, not time metrics.

**Calibration (diagnostic).** On the campaign host with the campaign
toolchain, without any cluster-forest observation (knotrel-benchmarks
`results/v1.1.0-cf5/timer-calibration/`):

| Quantity | Measured | Constant | Nature |
| --- | --- | --- | --- |
| Clock tick | deltas only 0, 41, 42, 83, 84, 125 ns (24 MHz counter) | `q` = 41.667 ns | a monotonic counter: the rounding error of one interval is below `q`, guaranteed |
| Clock read inside an interval | `Instant::now()` 13.9–14.1 ns; empty interval mean 14.3–14.5 ns; summed per-operation timing exceeds one interval by 14.9–15.1 ns per operation | `o` = 16 ns | largest mean observed, rounded up: an estimate |
| Per-operation harness work inside `workload_wall_ns` but outside the operation intervals (compact-bfs, every K1/V2/V3 workload, 5 repetitions, 2 runs) | candidate harness 18.8–33.2 ns; A harness candidate 19.1–25.8 ns; A harness v1.0.0 18.6–24.4 ns | `g` = 34, 26, 25 ns | largest observed, rounded up: an estimate |

Limits of the calibration: one host and one day; compact-bfs only, for `g`;
means, not worst cases, for `o`. The largest single empty interval observed
was 7.9–35 µs, which is preemption. Those numbers bound nothing beyond the
conditions measured.

**What `E` is.** For each metric, `E` estimates the systematic additive
error of one observed value. It is derived from the calibration and is
**not** a mathematically guaranteed upper bound. Only the `q` terms are
guaranteed. The `o` and `g` terms are calibrated estimates. The quantization
term of a per-operation sum is probabilistic: three standard deviations,
assuming independent tick phases.

| Category | Metrics | `E` |
| --- | --- | --- |
| Aggregate: `j` intervals, nothing timed inside | K2 `update_ns`, `query_ns` (`j` = 20); K2x, K3, L1, L3 imports (`j` = 1) | `j·(q + o)`: 1.15 µs; 58 ns |
| Aggregate around `k` individually timed operations | K1, V2, V3 `workload_wall_ns` (`k` = 400 to 10 000 by workload; the larger `g` of the two arms) | `q + o + k·(g + o)`: 17 µs to 500 µs |
| Sum of `k` per-operation latencies | L3 churn `observation_ns` (`k` = 570 151 or 750 000) | `k·o + 3·q·√(k/6)`: 9.2 ms; 12.0 ms |
| HTTP client percentile, one request interval | S1, V2, V3 `latency_ns.p99` | `q + o` = 58 ns |

The M_reg HTTP clients are closed loop. That design limits each client to
one request in flight; it does not remove scheduling or wake-up delays of
the client thread inside the request interval. Those delays, like the
client's request encoding and socket calls, are part of the latency
measured for both arms. They are not in `E`.

**What `δ` covers.** `δ = ln(1 + E/(cf − E)) + ln(1 + E/(ref − E))`, computed
on the arm medians, is the largest shift of the log ratio that an additive
error of at most `E` on each arm can cause. It treats the error as
symmetric and independent across arms, which is conservative for overhead
common to both arms. It excludes:

1. the loss of overlap between consecutive operations caused by per-operation
   timing (K1, V2, V3, L3 churn), reported separately below;
2. preemption, interrupts, frequency changes and client scheduling inside an
   interval. These are random, act on both arms, and enter the dispersion of
   the pairs, hence the interval. They are not bounded by `δ`;
3. errors larger than the calibrated `o` and `g`, if the campaign conditions
   differ from the calibration;
4. the difference between per-pair values and the medians used for `δ`;
5. host drift and bias common to both arms that is not overhead (section 6).

**Rule**, per metric:

1. If `min(cf, ref) ≤ 2E`: TIMER_LIMITED.
2. Otherwise compute the class of section 7 (or 7.1, for V2) on `[lo, hi]`
   and on `[lo − δ, hi + δ]`. If they differ, the metric is TIMER_LIMITED,
   and the class on `[lo, hi]` is published as `class_without_limit`,
   never counted. If they agree, that class stands.

Consequence (verified by tests, including at the margin with `δ` near
10⁻⁴): no class stands if a shift within the estimated limit would change
it. In particular, no PASS, EQUIVALENT, FASTER, SLOWER or REGRESSION is
produced where the instrumental sensitivity could change the
classification. INCONCLUSIVE stays INCONCLUSIVE, since widening cannot make
an interval decisive. TIMER_LIMITED keeps every value, counts as missing
evidence in section 12, and in V2 has the consequence of INCONCLUSIVE
(section 7.1). Because the rule rests on an estimate, a class that stands
means "not changed by the calibrated limit", not "immune to every
measurement error".

**Per-operation timing (not quantified, reported separately).** Timing each
operation stops consecutive operations from overlapping. In the calibration,
summed per-operation timing exceeded the aggregate by 63–77 ns per operation
for a 42–56 ns operation, against 15 ns for a near-empty one. The effect
depends on the operation and on the engine, so it cannot be a constant. It
is part of how v1.0.0 defined these metrics. It is not in `E` or `δ`. The
analyzer lists it in `not_in_limit` for every affected metric (K1, V2 and
V3 `workload_wall_ns`, L3 churn), and the CF5 report states it next to
those cells.

**Preparatory data (diagnostic, not results).** These are single pairs
from section 11, from tooling builds older than the frozen ones. They give
no class and no interval. Only `δ` is indicative, computed from one pair's
values. Since the rule is fixed, they are not used for anything else:

**Provenance.** The maintainer rejected the uniform 1 ms threshold

## 7. Classification

Margins (the existing tolerances, declared before any data): time
`m = 10 %`, tails (p99, query tail) `m = 25 %`, throughput `m = 10 %`,
memory `m = 20 %`.

Timed comparisons, interval `[lo, hi]` of the log ratio:

| Class | Rule |
| --- | --- |
| FASTER (higher throughput) | `hi < ln(1 − m)` |
| SLOWER | `lo > ln(1 + m)` |
| EQUIVALENT | `ln(1 − m) ≤ lo` and `hi ≤ ln(1 + m)` |
| INCONCLUSIVE | any other complete interval |
| TIMER_LIMITED | the metric is not resolvable at its margin given its measurement limit (section 6.1): no class, numbers kept; never counted as PASS or EQUIVALENT |

Deterministic comparisons (K4, L4), ratio `q`: SMALLER if `q ≤ 1 − m`,
LARGER if `q ≥ 1 + m`, otherwise SIMILAR; UNDEFINED (no class) when the
reference value is not positive (a net live size can be zero).

V1 and V2 use the v1.0.0 one-sided classes (section 7.1). L2 and S3 use
their own rules (section 4).

Every cell is published with its class, interval and medians, including
SLOWER, LARGER, INCONCLUSIVE, REGRESSION and FAIL; nothing is dropped,
pooled or reclassified after collection.

### 7.1 Regression checks (V1, V2): REGRESSION is not INCONCLUSIVE

With interval `[lo, hi]` of `ln(candidate / v1.0.0)` (throughput: inverted)
and the v1.0.0 tolerance `t`:

| Class | Rule | Meaning | Consequence for v1.1.0 |
| --- | --- | --- | --- |
| PASS | `hi ≤ ln(1 + t)` | No slowdown beyond `t`, at the stated confidence | None |
| REGRESSION | `lo > ln(1 + t)` | **Evidence** of a slowdown beyond `t` | Blocks the release until the cause is fixed and the cell re-qualified on a new candidate, or the maintainer accepts the regression explicitly, named in the release notes |
| INCONCLUSIVE | otherwise (`lo ≤ ln(1 + t) < hi`) | **No evidence either way**: the interval contains both acceptable and unacceptable slowdowns | Not a regression and not a pass. Needs a maintainer disposition: accept with disclosure (the interval published), or a targeted follow-up under a separately approved protocol on the same candidate. It is never rerun inside CF5 and never reported as a regression or a pass |

| TIMER_LIMITED (V2 only, section 6.1) | the class would change within the measurement limit | **No evidence either way** at the instrument's resolution | As INCONCLUSIVE: a maintainer disposition, never a pass or a regression |

V1 has no TIMER_LIMITED class: it keeps the frozen v1.0.0 analysis,
including its REPORT_ONLY metrics (section 6.1).

The classes are not merged in any summary: the release notes list
REGRESSION, INCONCLUSIVE and TIMER_LIMITED cells separately.

## 8. Execution order and the cap

**Cap: 15 hours of host time** for one attempt (approved by the
maintainer on 2026-11-24 from the preparatory estimate of section 11;
revision 1: 10 hours, revision 2: 12 hours). Blocks run in a
predeclared order of priority, so that a cap cuts the least important
cells:

1. **Tier 1:** the correctness smoke (section 5), then V1 and V2 (regression
   against v1.0.0).
2. **Tier 2:** K1, K2, S1, L1, S3.
3. **Tier 3:** K3, K4, L3, L4, L2, V3, K2x.

Blocks run one after another in this order; pairs are interleaved only
within a block, so a cap cuts the last blocks, not every cell of a tier.
The delegated blocks (V1, L2, S3) run at their place in the order, under the
same deadline, through their own collectors started by the runner. Like a
pair in progress, a collector that has started runs to its end. Each
session and each rerun writes to its own output directory. A collector that
exits with an error counts as a crashed collector (section 9). It is rerun
once from scratch, and a second failure stops the campaign like a
correctness FAIL. The runner refuses to start when a scheduled delegated
block has no collector command. S3 also has
its own cap of 90 minutes, about twice its estimate. If the cap is reached,
S3 is NONCONFORMING, its completed observations are kept, and comparisons
without their three observations get no verdict (as in v1.0.0 block Q). The
runner refuses to start a session when a scheduled collector needs an
environment variable that is unset (S3: the PostgreSQL admin URL).

**Delegated collectors** (prepared by `results/v1.1.0-cf5/prepare_cf5.sh`
in knotrel-benchmarks, with these values fixed before any observation):

- **V1:** the v1.0.0 A procedure with B = v1.0.0 and C = the candidate.
  There are two plans of 12 pairs per cell (`run_p0_aa.py --execute`, block
  1 then block 2) with no analysis in between, and session seeds 141240,
  141241, 141242 (block 1) and 141250, 141251, 141252 (block 2). It is
  analyzed once by `analyze_v100q_a.py` with the v1.0.0 A rules.
- **L2:** `run_lifecycle_qualification.py --profile final --only C
  --lifecycle-engines cluster-forest`, order seed 51240. That is 60
  executions: the 15 configurations × heap and RSS × the lifecycle and
  reference arms. It is analyzed by `analyze_lifecycle_qualification.py`
  with criteria C1–C4.
- **S3:** `run_cf5_s3.py`. It is the v1.0.0 block Q runner with the sides
  rebound: both run on the candidate server, with `LOAD_ENGINE=cluster-forest`
  on one and `compact-bfs` on the other, the seven cells each, three rounds,
  and the first side alternating. The evaluation refuses any observation
  whose recorded engine is not its side's. There are seven comparisons:
  Q1–Q4 on the CF side with the protocol's thresholds, and for the three L1
  cells with query clients (G100k C=16, G100k C=64, G10k C=16) CF median
  query throughput ≥ 90 % and median p99 ≤ 125 % of the compact-bfs
  medians of the same session. A failed observation makes each comparison
  that uses it FAIL. A missing observation or a zero reference median gives
  no verdict. Neither case is a PASS.

**When the cap is reached:**

- The pair in progress completes; no new pair starts.
- A cell with fewer than 24 pairs is **INCOMPLETE**: no class (no interval
  is computed on a partial sample, because n would depend on the stopping
  time), its pairs and medians are published and marked as such.
- A cell not started is **NOT_RUN**.
- The campaign is **incomplete**, and the second session (section 8.1) is
  the only way to complete it.
- CF6 treats an INCOMPLETE or NOT_RUN cell as **missing evidence**
  (section 12), never as a result.

### 8.1 Second session (predefined)

- **When:** only after a first session that ended at the cap, either the
  campaign cap or a delegated collector's own cap (S3). A session that was
  interrupted or stopped by a runner error is NONCONFORMING (section 9),
  not capped. No classes come from it, and no second session completes it.
- **Scope:** exactly the cells left INCOMPLETE or NOT_RUN by the first
  session, and nothing else. **A complete cell is never repeated**, whatever
  its class.
- **Conditions:** same candidate and baseline SHAs and binaries, same host,
  same tooling, the conformance checks of section 9 passed before it starts;
  it starts at most 14 days after the first session ends.
- **Method:** each cell from scratch with 2 warmup and 24 new pairs; the
  first session's partial pairs stay published as data, marked
  INCOMPLETE-session-1, and are never combined with the new pairs. Order:
  session 1's frozen schedule, restricted to these cells. The runner refuses
  a second session after a correctness FAIL, with another matrix, other
  binaries or checkouts, or more than 14 days after session 1.
- **Cap:** 8 hours of host time. Cells still incomplete at its cap stay
  INCOMPLETE or NOT_RUN for good; CF5 then closes with them listed as
  missing evidence.
- **Decision:** the maintainer may decline the second session; CF5 then
  closes immediately with the same listing. No third session exists. The
  runner enforces this: it accepts only a session 1 directory as the
  starting point, and it marks that directory when the second session
  starts, so a second session 2 is refused. The analyzer accepts a second
  run only if it is the session 2 resumed from the first. The second session
  runs from the first session's campaign directory and tool map, so it uses
  the same binaries.

### 8.2 Overall budget

| Item | Cap (host time) |
| --- | --- |
| First session | 15 h |
| Second session (only if needed) | 8 h |
| **Campaign maximum** | **23 h**, plus at most one NONCONFORMING attempt repeated (section 9) |

## 9. Attempts and validity

- At most two attempts: the first, and a second from scratch only if the
  first is NONCONFORMING. Each attempt has its own campaign directory
  (`prepare_cf5.sh CAND FREEZE 1|2`), and the prepare step verifies the
  freeze. The freeze commit may only add `FREEZE.json`, which names the
  candidate, the tooling commit and the matrix hash. Before its first
  observation, the runner refuses to start when the candidate checkout or
  the matrix differs from that record, or when a checkout is dirty. A cell may be rerun **once** within an attempt,
  only for an infrastructure failure (recorded host interference, a crashed
  collector), never because of its result; the rerun replaces the whole
  cell.
- **Conformance** (as v1.0.0 §5.4): candidate and baseline SHAs and binary
  hashes match the record; the host is idle (load average, CPU frequency
  and temperature recorded before and after each block); no swap. A failed
  check makes the attempt NONCONFORMING: no classes are published from it.
  Two NONCONFORMING attempts leave CF5 not completed, for a maintainer
  decision.
- No rule, margin, cell, size or order changes after the first
  observation.

## 12. CF6 adoption criteria (declared now)

CF6 is a maintainer decision informed by CF5. The rules below fix what each
possible decision requires; they are applied to the CF5 classes as
published, without adjustment.

**Default outcome.** `cluster-forest` stays opt-in and experimental, and
`compact-bfs` stays the default. This holds unless the conditions of a
different outcome are all met.

**Selection guidance (published with v1.1.0).** Families, each judged
separately against each reference engine:

| Family | Primary cells (count toward a preference) | Veto-only cells (any opposite class makes it mixed) |
| --- | --- | --- |
| each K1 workload (8) | its K1 cells (2 sizes) | — |
| K2 d4, K2 d16 | the K2 cells (update time first) | K3 construction and K4 memory of the same graphs |
| K2x | its cells | — |
| K3 families | the 6 K3 cells on K1 family graphs | — |
| L (lifecycle) | L1 and L3 cells | L4 memory |
| S1 lifecycle off; S1 lifecycle on | their S1 cells (throughput first) | — |

V, S3 and L2 have their own rules and no statement. Let **P** be the class
of each primary cell's first metric (or its state, for a cell without a
class) and **A** every metric class (or state) of every cell of the family.
Exactly one statement, decided by these rules in order:

| Statement | Rule |
| --- | --- |
| **Mixed results** | A has at least one FASTER or SMALLER and at least one SLOWER or LARGER |
| **Insufficient evidence** | A has an INCOMPLETE, NOT_RUN, TIMER_LIMITED, INCONCLUSIVE, UNDEFINED or FAILED element |
| **Prefer `cluster-forest`** | P is all FASTER/SMALLER or EQUIVALENT/SIMILAR with at least half FASTER/SMALLER (and, by the first rule, nothing in A is SLOWER or LARGER) |
| **Prefer *reference*** | the same with SLOWER/LARGER |
| **No difference beyond the margins** | every element of A is EQUIVALENT or SIMILAR |
| **Isolated differences** | any other case: differences in one direction only, below the half a preference needs; the differing cells are listed |

The rules are applied in this order and exactly one statement results; the
last row makes the set exhaustive. The analyzer names, with each statement,
the cells whose classes go against it (and, for isolated differences, the
differing cells). No statement is produced when a session failed the
correctness gate.

"Mixed results" (measured differences in both directions) and
"insufficient evidence" (no conclusion possible from the data) are distinct
statements and are never merged. A family whose only non-conclusive cell
is INCONCLUSIVE is "insufficient evidence", not "no difference".

**Perimeter.** Every statement is limited to what was measured: the
workload family, the sizes and densities in the matrix, the host recorded
in the campaign, the candidate SHA and the server configurations used. The
guidance states that perimeter next to each statement and does not
extrapolate to other sizes, graph shapes, hardware, concurrency levels or
releases. Isolated cells that disagree with the rest of their family are
named, not turned into a recommendation (section 6, multiplicity).

**Promotion to a non-experimental engine.** Not eligible in v1.1.0, which
introduces the engine. Eligible from a later minor release only if: no
correctness failure in CI, the long workflow, the soak tests or any
qualification since the merge of PR #150; CF6 guidance with no "prefer
reference" for CB on the feeder scenarios (S3) and the lifecycle blocks
(L1, L3); a qualification of that release with the same rules; and an
explicit maintainer decision.

**Change of the default engine.** Out of scope for v1.1.0. It requires a
prior promotion, CF not SLOWER than CB in any K1, K2, S1 or S3 cell and
not LARGER in any K4 or L4 cell, evidence on Knotrel's own workloads (the
feeder scenarios and a user-representative trace), a dedicated
qualification, and an explicit maintainer decision.

**Regression findings.** V1 and V2 outcomes follow section 7.1, whatever
CF6 decides about `cluster-forest`: a REGRESSION blocks the release until
fixed or explicitly accepted; an INCONCLUSIVE needs a disposition (accept
with disclosure or an approved follow-up), and is reported as missing
evidence, not as a regression.

## 13. Exploratory workload: provenance and separation

**Provenance.** During the independent review of the CF2 code
(2026-11-24), the reviewer (an AI agent instructed to review adversarially,
working on a copy of the crate) wrote an ad hoc timing loop: random simple
graphs with `E = 3V`, all edges inserted in a random order then all deleted,
release build, sizes 2^12 to 2^18, one development machine, single runs, no
reference engine, no protocol. It reported cut time divided by `log² N`
within 24–29 ns, about 1.6–3.0 pushes per edge and about 2.3 levels per
cut (ADR 0014 §12). The scenario follows the insert-all/delete-all shape of
the paper's §8.2 experiments.

**Treatment.**

- The scenario is **not excluded**: it is a plausible stress case (dense
  enough for replacement searches, sparse enough to scale), so it is
  measured anew as K2x, under this plan's method, against every reference
  engine, at sizes inside (2^14, 2^17) and outside (2^20) the observed range.
- The **exploratory data stay separate**: they are not stored as campaign
  evidence, not pooled with K2x, not used as a baseline or a prior, and
  not compared statistically with any CF5 result. They remain only in ADR
  0014 §12, labeled exploratory.
- K2x gets the same margins and classes as every other cell. Nothing in
  this plan (margins, sizes, densities, n, cap, CF6 rules) was set from the
  exploratory numbers. The plan's author knew of the observation when
  writing it; this is disclosed here.
- A flat normalized cost over a finite range does not demonstrate the
  asymptotic bound, whichever data show it; CF5 makes no asymptotic claim.
