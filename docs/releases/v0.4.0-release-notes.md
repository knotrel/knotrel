# Knotrel v0.4.0 Release Notes — Observability & Performance

**Release candidate:** v0.4.0 is not yet published. Versions are 0.4.0 and M6
was accepted on 2026-11-15.

**Regression qualification:** the qualification against v0.3.0 (roadmap
0.4.2.3) ran on candidate `62c2cea`. It did **not** pass unconditionally:
- one cell is a REGRESSION;
- two cells are UNRESOLVED;
- the maintainer accepted all three explicitly for this release.

See [Regression qualification against v0.3.0](#regression-qualification-against-v030).

**Identity of the release commit:** the release commit adds documentation
changes on top of `62c2cea`. Comparative builds showed identical executed
code and symbol addresses for the server, the end-to-end driver, the core
benchmark harness and the metrics probe. The only differences are panic line
numbers, build-time strings and signing metadata.

**Still outstanding:**
- CI and the release dry run on the exact release commit;
- the repeated deployment check;
- maintainer release approval.

## Scope

v0.4.0 completes integration-aware observability (roadmap M6) and ships the
hot-path optimizations that passed review and before/after measurement
(Feature 0.4.1). Client-visible HTTP contracts are unchanged: routes, status
codes, bodies, headers, error messages and batch semantics are the same as in
v0.3.0. Local persistence moves to v0.5.0; node/edge lifecycle (M10) and a
concurrency redesign (M5) are not part of this release.

## Observability

- **Prometheus metrics (M6.2, opt-in).** `KNOTREL_METRICS_ENABLED=true` serves
  `GET /metrics`: HTTP requests and server-side duration, pre-execution
  rejections by reason, uncertain outcomes by cause, graph-job backlog and
  capacity, queue/lock-wait/execution time per job kind, graph operations and
  feeder events by outcome, feeder rejections by code, desynchronizations by
  cause, graph node and edge counts, readiness state, worker failure, feeder
  lease remaining and last-applied age, import progress, results and phase
  durations, and catch-up duration. Every label is a compile-time enumeration;
  the series count is bounded (at most 1,414 standalone and 1,834
  source-managed) and independent of graph size, requests, generations and
  sessions. Disabled by default; with metrics disabled no accounting work is
  added. See the [observability contract](../observability-contract.md).
- **Structured logs (M6.3).** Every request runs in a `request` span with a
  process-unique `request_id`, the route and, when known, `generation`,
  `state_version` and `sync_status`. Blocking workers log inside the
  submitting request's span. New lines report synchronization transitions,
  import publication, feeder rejections by code and lease expiry; a dropped
  request logs `request cancelled before response`. Graph payloads, feeder
  session IDs and error messages quoting caller input are never logged;
  caller-supplied identifiers are escaped and truncated. `LOG_FORMAT=json`
  selects JSON lines ([contract section 17](../observability-contract.md#17-m63-structured-logs-released-in-v040)).
- **Alert rules (M6.4).** [`examples/observability/prometheus-alerts.yml`](../../examples/observability/prometheus-alerts.yml)
  with ten rules (worker failure, saturation, busy rejections, 5xx ratio,
  feeder loss, desynchronization, declared gaps, slow bootstrap, readiness
  flapping, repeated feeder rejections) and a [runbook](../alerting.md).
- **Qualification (M6.5).** Under a budget approved before measurement
  (paired median ≤ 3%, 95% interval upper bound ≤ 6%), enabling metrics passed
  in all six in-process router scenarios; the largest cost was +1.28%
  [+0.60%, +1.59%] on a batch of 1,024 queries
  ([campaign](../../../knotrel-benchmarks/results/metrics-overhead-20261115/README.md)). The series count stays
  constant under sustained churn of sessions, generations and node IDs
  ([contract section 18](../observability-contract.md#18-m65-qualification-overhead-and-series-count)).
- **Re-run on the release candidate (G7-V).** The same budget was applied to
  candidate `62c2cea`, with a probe built with the shipped server's `axum`
  features. All six scenarios passed. The largest cost was +1.24% [+0.63%,
  +2.24%] on a batch of 1,024 cut/link operations.
  - **Procedural deviation:** a first run had agent activity during the
    untimed build and the quiet period. It also passed all six scenarios. It
    is retained, but the evaluated result is the repeat.
  - **`single_connected`:** it measured about 11% faster with metrics
    enabled. Its cause is not established, and no speedup is claimed.
  - **Scope:** an in-process probe on one host. It does not measure network,
    log-sink or production-host overhead.

## Performance

The [hot-path audit](../archive/hot-path-audit-v0.3.0.md) reduces allocations, copies,
lookups and lock work on request, import and feeder paths without changing
results. Measured against v0.3.0-era baseline `e1e1181` with a same-binary
A/A arm on one Apple M3 host ([campaign](../../../knotrel-benchmarks/results/hot-path-audit-20261114/README.md)):

- allocations per request fall 16.7% (single query) to 75.0% (100,000-node
  import);
- in-process router: import −21%, feeder batch of 1,024 events −14% to −19%,
  batches of 1,024 queries or cut/link −6% to −9% (confirmed, metrics off and
  on); single-request latency is unchanged within noise;
- core bulk initialization: `compact-bfs` −6% to −7%, `ett-scan` and `hdt`
  sustained-churn −4% (confirmed); chain initialization on `ett-scan`/`hdt`
  inconclusive;
- end-to-end peak RSS during import −4.7% (marginal); other end-to-end
  timings inconclusive.

One marginal regression flagged by the campaign did not reproduce in a
pre-specified re-measurement ([re-check](../../../knotrel-benchmarks/results/hot-path-recheck-20261115/README.md)).
All results are joint effects of the change set; they are not attributed to
individual changes and do not transfer to other hosts without
re-measurement.

**These audit results compare against `e1e1181`, not against v0.3.0.** The
regression qualification below compares the release candidate with v0.3.0:
- it found one REGRESSION;
- no cell met its criterion for citing an improvement.

**This release makes no general performance-improvement claim relative to
v0.3.0.**

**Report-only metrics.** The core `link` and `cut` p99 latencies of the four
core cells are reported but not gated. Their medians are within two ticks of
the host timer, so no percentage bound is established for them.

**Maintainer dispositions.** These are post-result waivers for this release
only, limited to the measured conditions. They are not a pass of the
regression gate, and they set no precedent for future releases.

- **D1, REGRESSION:** the sparse-traversal workload on `compact-workspace` is
  28.9% slower.
  - **Affected API:** the library API `Graph::connected_with_workspace` with
    `BfsWorkspace`. `knotrel-server` does not use it.
  - **Diagnostics,** which are not acceptance evidence:
    - identical machine instructions for the measured function;
    - equal instruction counts, with the extra time spent in extra CPU
      cycles;
    - diagnostic builds that changed code alignment removed the difference
      by slowing v0.3.0.

    This shows sensitivity to binary layout. It does not isolate data
    layout, called code or the hardware mechanism, and it does not make the
    regression harmless.
  - **Impact:** applications calling this API may see slower connectivity
    queries. The size and direction of the effect in other binaries are not
    known.
- **D2, UNRESOLVED:** `compact-bfs` connectivity p99 on sparse traversal.
  - **Affected path:** `Graph::connected`, which is the default engine of
    `ConnectivityGraph` and of the server.
  - **What is not established:** a 25% bound on this tail latency relative to
    v0.3.0.
  - **Diagnostics:** an intermittent slow state, with the same instructions
    and more cycles. It appeared in both versions, with different
    frequencies.
  - **Cause:** not established. Address-space randomization is an
    unverified hypothesis.
- **D3, UNRESOLVED:** HTTP request p99 for standalone batches of size 1.
  - **What is not established:** a 25% bound relative to v0.3.0.
  - **Observed pattern:** the values depended strongly on the launch
    position within each measured pair, in both versions. No cause is
    attributed.

**Not covered by this qualification:**
- the HTTP server with `KNOTREL_ENGINE=ett` or `hdt`, which has **no
  performance qualification**;
- `compact-workspace` through HTTP;
- `/metrics` enabled (covered separately by the G7-V re-run above);
- JSON logs, non-`info` filters and log sinks with backpressure;
- other hosts, targets and CI-built binaries.

**ETT/HDT core changes:** the gate's nine cells use `compact-bfs` and
`compact-workspace` only. The ETT/HDT core changes are covered only by the
separately reported hot-path audit evidence above. That evidence has these
limitations:
- a different baseline (`e1e1181`);
- different statistics;
- its own harness;
- a limited-facade initialization path.

## Distribution and platform coverage

Both crates and release archives use the [Elastic License 2.0](../../LICENSE.md).
The server and development toolchain use Rust 1.100.0; `knotrel-core` retains
its Rust 1.98.1 minimum supported version. Release targets are unchanged from
v0.3.0 (Linux x86_64, macOS Apple Silicon, Windows x86_64). Measurements were
taken on one Apple M3 host and do not transfer to other hosts without
re-measurement.

## Operational and release limitations

- There is no authentication, authorization or TLS. `/metrics` is
  unauthenticated and served on the same listener: keep it inside the trust
  boundary.
- There is no durable graph persistence (planned evaluation: v0.5.0).
- No source-relative lag metric exists; `feeder_last_applied_age_seconds`
  measures inactivity, not lag.
- Alert thresholds are starting points, not service-level objectives. The
  rules file is checked against the exported series in the test suite but is
  not validated with `promtool` in CI.
- Log fields are an operational interface, stable within a minor release, not
  a machine contract.
- Performance qualification against v0.3.0 has one accepted REGRESSION
  (D1) and two accepted UNRESOLVED results (D2, D3). See
  [Regression qualification against v0.3.0](#regression-qualification-against-v030).
