# Knotrel v0.7.0 Release Notes — Measured Concurrency

**Status: DRAFT, not accepted. Qualification NOT CONFORMING; maintainer
decision pending.** The frozen qualification campaign against published
v0.6.0 ran, but its experimental conformance is not met (see Performance
qualification). None of its results can be accepted. A conforming
re-collection of the whole campaign is proposed and not started.
No maintainer waiver or acceptance from v0.6.0 or earlier applies.

## Scope

v0.7.0 addresses the concurrency bottleneck measured in v0.6.0: the single
graph mutex serialized read-only work, and lock wait was 85–101% of client
latency at 16 or more clients (roadmap M5, 0.7.1–0.7.3). It also evaluates
the 0.7.4 performance candidates with the v0.6.0 method.
Design: [v0.7.0 design and plan](../superpowers/plans/2026-11-17-v0.7.0-measured-concurrency.md).

It adds no public Rust item, HTTP field or route, error code, environment
variable or metric. Not in this release: admission changes (a permit
reserved for the feeder), a batch ceiling, persistence, multi-graph and
lifecycle support for `ett`/`hdt`.

## What changed

- **Read-only requests run in parallel** (`knotrel-server`, 0.7.4a). The
  graph lock is a read-write lock (`parking_lot::RwLock`, already a
  dependency). `POST /v1/operations` and `POST /v1/batch` requests whose
  operations are all queries (`connected`, `node_state`, `edge_state`) and
  `GET /v1/stats` take it shared; every other request takes it exclusively.
  - Results are still equivalent to some sequential order of whole requests,
    and a batch is still one indivisible unit.
  - While a state-changing request waits, new queries wait behind it, so
    queries cannot starve the feeder or imports.
  - A batch that contains any mutation still takes the whole graph
    exclusively.
  - **Panic behavior:** a panic in any graph job still makes the instance
    unavailable to every job that acquires the lock afterwards. New in
    v0.7.0: read-only requests already running in parallel with a panicking
    read-only request complete normally; it could not change the state they
    read.
- **Import parsing with `sonic-rs`** (`knotrel-server`, 0.7.4b; aimed at the v0.6.0 import parse cost, performance not yet qualified). `POST
  /v1/feeder/import` bodies are decoded with `sonic-rs`; a body it rejects
  falls back to the v0.6.0 `serde_json` and `simd-json` path, so every error
  status and message is unchanged. Import memory is unchanged.
  `sonic-rs` becomes a dependency of `knotrel-server` (not of
  `knotrel-core`).

- **Catalog tombstone handling** (`knotrel-core`, `LifecycleGraph`; added
  after the re-qualification, diagnostic D2c). Under fresh-ID churn, catalog
  removals leave hash-table tombstones that used to make the catalog table
  double although live entries stayed constant: at 100,000 nodes, from
  131,072 to 262,144 buckets within the first few percent of churn. That
  growth caused the C3 heap-growth FAILs.
  - **Now:** an insert that would grow the table rebuilds it instead, sized
    for its live entries (the same size under churn, never larger), when
    they are at most 90% of its full capacity. The
    rebuild is `O(V)`, amortized `O(1)` per insertion.
  - **Effect in diagnostic D2c** (100,000 nodes, fresh-ID churn, 6,000
    cycles; not a qualification result):
    - peak and steady-state heap about 5 MiB lower;
    - construction unchanged;
    - C3 rule values within budget;
    - catalog rebuilds with a median of about 0.7 ms and a maximum of 6.5 ms,
      against engine compactions of up to 72 ms in the same runs;
    - B1 fresh-churn windows within ±0.5% of the previous code.
  - No API change.

Evaluated and not adopted (design §11): a hand-written `serde` visitor (not
faster), `arc-swap` snapshots (one extra graph per feeder batch), a different
global allocator (`mimalloc` is already the server allocator; dropped by the
maintainer), CSR adjacency (dropped by the maintainer).

## Compatibility

No client-visible change in any configuration, other than timing and the
panic nuance above. `knotrel-core` changes only internally (catalog tombstone
handling); its MSRV stays 1.98.1.

## Costs and resource limits

- A `connected` is still an `O(V + E)` BFS. Parallel queries use more CPU
  cores and memory bandwidth at once; a query-only batch no longer waits for
  other query-only batches.
- A state-changing request waits for the query requests already holding the
  lock (at most about one query batch), then blocks new queries while it
  runs.
- With many hot-retrying clients, admission still reserves no permit for
  feeder requests (disclosed in v0.6.0; v1.0 envelope work).
