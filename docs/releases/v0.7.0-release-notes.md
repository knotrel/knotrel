# Knotrel v0.7.0 Release Notes — Measured Concurrency

**Status: released on 2026-11-20 (GitHub Release `v0.7.0`, crates.io).
Qualification ACCEPTED WITH EXCEPTIONS (accettato con eccezioni) on
2026-11-20.** The
conforming qualification against published v0.6.0 did not pass every gate:
three INCONCLUSIVE results and two unqualified requirements are accepted by
the maintainer for v0.7.0 only (see Maintainer decisions). This is not a
complete qualification. No waiver from v0.6.0 or earlier applies.

## Scope

v0.7.0 addresses the concurrency bottleneck measured in v0.6.0: the single
graph mutex serialized read-only work, and lock wait was 85–101% of client
latency at 16 or more clients (roadmap M5, 0.7.1–0.7.3). It also evaluates
the 0.7.4 performance candidates with the v0.6.0 method.
Design: [v0.7.0 design and plan](../superpowers/plans/2026-11-17-v0.7.0-measured-concurrency.md).

It adds no public Rust item, HTTP field or route, error code, environment
variable or metric. Not in this release: admission changes (a permit
reserved for the feeder), a batch ceiling, persistence, multi-graph and
lifecycle support for `ett`/`hdt`.

## What changed

- **Read-only requests run in parallel** (`knotrel-server`, 0.7.4a). The
  graph lock is a read-write lock (`parking_lot::RwLock`, already a
  dependency). `POST /v1/operations` and `POST /v1/batch` requests whose
  operations are all queries (`connected`, `node_state`, `edge_state`) and
  `GET /v1/stats` take it shared; every other request takes it exclusively.
  - Results are still equivalent to some sequential order of whole requests,
    and a batch is still one indivisible unit.
  - While a state-changing request waits, new queries wait behind it, so
    queries cannot starve the feeder or imports.
  - A batch that contains any mutation still takes the whole graph
    exclusively.
  - **Panic behavior:** a panic in any graph job still makes the instance
    unavailable to every job that acquires the lock afterwards. New in
    v0.7.0: read-only requests already running in parallel with a panicking
    read-only request complete normally; it could not change the state they
    read.
- **Import parsing with `sonic-rs`** (`knotrel-server`, 0.7.4b; aimed at the v0.6.0 import parse cost; HTTP lifecycle imports measured 16–20% faster than v0.6.0 in qualification 3; the share due to `sonic-rs` is not isolated). `POST
  /v1/feeder/import` bodies are decoded with `sonic-rs`; a body it rejects
  falls back to the v0.6.0 `serde_json` and `simd-json` path, so every error
  status and message is unchanged. Import memory is unchanged.
  `sonic-rs` becomes a dependency of `knotrel-server` (not of
  `knotrel-core`).

- **Catalog tombstone handling** (`knotrel-core`, `LifecycleGraph`; added
  after the re-qualification, diagnostic D2c). Under fresh-ID churn, catalog
  removals leave hash-table tombstones that used to make the catalog table
  double although live entries stayed constant: at 100,000 nodes, from
  131,072 to 262,144 buckets within the first few percent of churn. That
  growth caused the C3 heap-growth FAILs; in qualification 3, C3 passes in
  all 15 cells.
  - **Now:** an insert that would grow the table rebuilds it instead, sized
    for its live entries (the same size under churn, never larger), when
    they are at most 90% of its full capacity. The
    rebuild is `O(V)`, amortized `O(1)` per insertion.
  - **Effect in diagnostic D2c** (100,000 nodes, fresh-ID churn, 6,000
    cycles; not a qualification result):
    - peak and steady-state heap about 5 MiB lower;
    - construction unchanged;
    - C3 rule values within budget;
    - catalog rebuilds with a median of about 0.7 ms and a maximum of 6.5 ms,
      against engine compactions of up to 72 ms in the same runs;
    - B1 fresh-churn windows within ±0.5% of the previous code.
  - No API change.

Evaluated and not adopted (design §11): a hand-written `serde` visitor (not
faster), `arc-swap` snapshots (one extra graph per feeder batch), a different
global allocator (`mimalloc` is already the server allocator; dropped by the
maintainer), CSR adjacency (dropped by the maintainer).

## Compatibility

No client-visible change in any configuration, other than timing and the
panic nuance above. `knotrel-core` changes only internally (catalog tombstone
handling); its MSRV stays 1.98.1.

## Performance qualification

**Outcome: accepted with exceptions, for v0.7.0 only.** This is not "all
gates PASS", and not a complete qualification. Single decision record:
knotrel-benchmarks `results/v0.7.0-qualification-3/DECISIONS.md`.

- **Campaign.** Qualification 3, attempt q3-3, 2026-11-20. Candidate
  `fa5f3a9` against published v0.6.0 (`5db9ec4`); tooling and freeze
  knotrel-benchmarks `0be54716`; Apple M3, macOS.
- **Conformance.** CONFORMING: 756 measured units, none invalidated, under a
  proportional host-interference policy declared before collection.
  - The earlier attempts q3-1 and q3-2 did not conform and are not used.
  - The earlier campaigns (the first campaign and the re-qualification) are
    kept for the record; no result of theirs is used.

|---|---|

| B1–B4 timing (deciding) | 58 PASS, 1 INCONCLUSIVE (accepted) |
| B5 memory, C1, C2 | all PASS |
| C3 heap growth under churn | 15/15 PASS (the three v0.6.0 FAILs are resolved) |
| C4 RSS (disclosure category) | 9 PASS, 6 EXCEEDS_BUDGET |

**Accepted with exceptions** (maintainer, 2026-11-20; for v0.7.0 only, no
precedent):
- **B4 `metrics-ops`, sparse 10k: INCONCLUSIVE.** 2.71 → 2.83 ms, +6.5%
  [+1.7%, +7.4%] against a 6% budget.
- **R `core-import`, 10k: INCONCLUSIVE.**
  - sparse: 970 → 947 µs, −1.7% [−17.6%, +14.2%];
  - hub: 788 → 802 µs, +3.1% [−17.9%, +24.7%];
  - both against 10%.
- **B4 lifecycle batches (`ops`) and feeder events (`events`) on `hub` 10k:
  not qualified by comparison.** v0.6.0 cannot offer the candidate's
  atomicity there. Two hub deactivations expand to more plain operations
  than one plain request can carry, so no equivalent reference exists.
  - **Indicative evidence only, with limits** (decision record §4 D3):
    against references that are not atomic, ops is +4.0% or −6.8% and
    events +5.0% or −6.4%, depending on the reference variant.
  - **No status is derived** from these comparisons.

The INCONCLUSIVE results stay INCONCLUSIVE; they do not become PASS.

**Disclosed, unchanged categories:**
- **C4 RSS EXCEEDS_BUDGET ×6.** Allocator retention under fresh-ID churn
  (and hub same-ID churn at 100k). The heap rule (C3) passes for the same
  workloads.
- **B4 `import-high` descriptive REGRESSION, +408%** (1.52 → 7.66 ms per
  10k-node import with 60% inactive and 30% disabled entries).
  - **Baseline:** v0.6.0's frozen reference, which imports only the
    effective graph and does not validate or keep the registered topology.
  - **Against a capability-equivalent reference:** +57.8% [+54.3%, +63.1%],
    PASS at 100%.
  - **History:** recurs since v0.5.0.
  - **Impact:** a per-import cost (about 6 ms per such import on the
    measured host), not on the query path.
- **B4 `ops` sparse 100k (descriptive): INCONCLUSIVE**, +19.9% against 25%.
  Its deciding equivalent cell passes.

**What improved, as measured on this host:**
- **Read-heavy contention** (M_reg):
  - 4 clients, 10k nodes: 15,289 → 32,232 req/s; p99 0.53 → 0.26 ms;
  - queries during an import or feeder events, 100k nodes: 4.5–5.2× the
    throughput, with p99 15–44% lower.
- **HTTP lifecycle imports** (R): 16–20% faster.
- **Fresh-ID churn:** 4–5% faster; compaction pauses 6–11% shorter; churn
  heap peaks 12–17% lower (Rmem).

Write-heavy and mixed workloads are unchanged within tolerance.
v0.7.0 is not claimed to be faster in general.

**Evidence applies to the release code.** The release commit's `crates/`,
`Cargo.toml` and `Cargo.lock` are identical to the measured `fa5f3a9`. The
release keeps `fixedbitset` 0.5.7, the measured version (`main` had bumped
it to 0.5.9); the bump is re-applied after the release.

## Costs and resource limits

- A `connected` is still an `O(V + E)` BFS. Parallel queries use more CPU
  cores and memory bandwidth at once; a query-only batch no longer waits for
  other query-only batches.
- A state-changing request waits for the query requests already holding the
  lock (at most about one query batch), then blocks new queries while it
  runs.
- With many hot-retrying clients, admission still reserves no permit for
  feeder requests (disclosed in v0.6.0; v1.0 envelope work).
