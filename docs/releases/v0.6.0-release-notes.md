# Knotrel v0.6.0 Release Notes — Lifecycle Efficiency & Measured Concurrency

**Status: released 2026-11-17** ([GitHub Release](https://github.com/knotrel/knotrel/releases/tag/v0.6.0);
[`knotrel-core` 0.6.0](https://crates.io/crates/knotrel-core/0.6.0) and
[`knotrel-server` 0.6.0](https://crates.io/crates/knotrel-server/0.6.0) on
crates.io). Accepted by the maintainer on 2026-11-17. The qualification did **not pass
unconditionally**; every non-PASS result is accepted as a disclosed limitation
under [Maintainer decisions](#maintainer-decisions). No maintainer waiver from
v0.5.0 or earlier applies.

## Scope

v0.6.0 makes node and edge lifecycle support (v0.5.0) and graph imports
cheaper, states their resource behavior precisely, and measures contention
and batching (roadmap M5 measurement, deferred M3.6) before any
synchronization change. It adds no public Rust item, HTTP field or route,
error code, environment variable or metric. With the default configuration,
clients see no behavior change.

Not in this release: any synchronization change. The coarse graph mutex is
kept by maintainer decision (2026-11-16); concurrency moves to v0.7.0.
Persistence, multi-graph and lifecycle support for `ett`/`hdt` are also out
of scope; `ett` and `hdt` stay rejected for lifecycle support.

## What changed

- **One-pass lifecycle engine build** (`knotrel-core`). Flagged imports
  (`LifecycleGraph::try_from_topology`) and engine compactions build the
  `compact-bfs` engine directly from the catalog: engine indices in ascending
  node-ID order, each effective edge found once, adjacency allocated once. The
  previous build replayed an effective-edge list through `add_node`/`link`.
- **Retired engine slots release their memory.** A removed node's isolated
  engine vertex no longer keeps its adjacency allocation until compaction. The
  compaction threshold is unchanged (`max(V, 1024)` retired slots), and engine
  vertices stay at most `2V + 1024`.
- **Streaming import parse** (`knotrel-server`). `POST /v1/feeder/import`
  bodies are decoded with `serde_json`'s streaming deserializer instead of
  `simd-json`'s tape. The tape's working set was several times the body. A
  body that `serde_json` rejects is parsed again with `simd-json`, so every
  error status and message is unchanged (differential test on a fixed corpus);
  invalid bodies pay a second parse. `serde_json` becomes a direct dependency;
  it was already in the dependency tree through `axum`.
- **Replaced graph released after the lock.** A replace import frees the old
  graph after releasing the graph lock, still inside its worker, so drain
  accounting covers it. Publication remains atomic.
- **Documentation.**
  - The lifecycle contract states the storage model with live state, retained
    capacity, temporary peaks, allocator retention and RSS kept apart, and
    gives a hash-table capacity bound under churn
    ([lifecycle contract §5](../topology-lifecycle.md#5-engines-complexity-and-storage)).
  - The feeder-events example in `http-api.md` gains the required
    `prev_source_position`.

Evaluated and rejected: compacting at `max(V/4, 1024)` retired slots (made
fresh-ID churn about 90% slower) and reserving engine room on rebuild (higher
steady memory and compaction peak); both are reverted.

## Compatibility

No client-visible change in any configuration. The only behavioral difference
is internal: an import body that `serde_json` rejects is parsed twice, which
costs extra CPU but never more memory than v0.5.0 used for every import.
Engine index order changed; no result depends on it.

(`51e3b4d`), 2026-11-16, Apple M3, macOS 26.5.2, rustc 1.100.0, AC power.

## Costs and resource limits

- Lifecycle operation costs are as in v0.5.0, except two items. A compacting
  removal now costs a one-pass `O(V log V + E)` rebuild under the graph lock
  (amortized `O(log V + E/V)` per removal). Retired slots keep only an ID-map
  entry and an empty vector header.
- HTTP import memory is about the body while it is parsed, then the decoded
  request, the catalog and the new engine, beside the old graph until just
  after publication. Size memory for `old graph + body + new graph`; process
  RSS still has no hard bound.
- Under fresh-ID churn the catalog hash table can double once and then stays
  bounded by the maximum registered node count (lifecycle contract,
  *Hash-table capacity under churn*).
- A `connected` is an `O(V + E)` BFS under the single graph lock. Large
  batches and many clients queue behind it (comparison §7).

## Maintainer decisions

**Maintainer decision (2026-11-17): every item below is accepted as a
disclosed limitation of v0.6.0** (the "accept with disclosure" option of the
comparison report, §8, where one is listed).

- Frozen verdicts are unchanged. Each REGRESSION, FAIL, UNRESOLVED and
  INCONCLUSIVE result stays as reported, and no speedup or pass is claimed for
  those cells.
- The acceptance covers v0.6.0 only and is not a waiver for later releases.
- Fixes already planned stay on v0.7.0 (ROADMAP 0.7.4b and 0.7.4c).

1. **R HTTP import 100k 60/30: REGRESSION**, +13.44% [+12.55, +14.02]. This
   is the cost of the streaming parse on flagged object entries, traded for
   −76% peak memory. A candidate fix (`sonic-rs` or a hand-written visitor)
   is planned for evaluation in v0.7.0 (ROADMAP 0.7.4b). That plan does not
   decide this item for v0.6.0.
2. **B4 `import-high`: REGRESSION**, +419.9% against an effective-graph-only
   reference (v0.5.0: +444.8%). It is inherent to the full-topology contract.
3. **C3 heap growth: FAIL** ×3 (fresh-ID churn at 100k, slope +0.103 /
   +0.172 / +0.119 against 0.10). A bounded one-time table doubling plus the
   pre-compaction sawtooth; peaks are lower than v0.5.0.
4. **A batch 1: UNRESOLVED** (request p99, wide interval) and **A batch 256:
   UNRESOLVED** (sampled RSS upper bound +22.16% against 20%). There is no
   code change on these paths.
5. **A `compact-workspace` traversal and startup: INCONCLUSIVE_DISCLOSED.**
6. **B4 `metrics-ops`: INCONCLUSIVE**, +5.57% [+1.83, +9.42] against 6%.
7. **C4 RSS** disclosures (8/15). An allocator candidate (`mimalloc` or
   `jemalloc`) is planned for evaluation in v0.7.0 (ROADMAP 0.7.4c).
8. **Contention coverage defects:** in the frozen campaign, feeder catch-up
   was not measured at 100k, and 10k import overlap was not measured with 16
   or 64 clients. The declared supplementary run (comparison §9) measured
   them, but it does not conform to its protocol (concurrent automated
   `git fetch`).
   - Its two M_reg PASS results are evidence with limitations and are not
     proposed for acceptance.
   - The conforming rerun of those two cells PASSes. **Maintainer decision
     (2026-11-17): accepted** as the coverage evidence for this item, with
     the disclosed residual activity and the confirmed small degradation
     within tolerance in the feeder catch-up cell.
   - **Status: dispositioned.** The frozen verdicts and the other items are
     unchanged by this decision.
   - The no-priority finding for the feeder goes to v0.7.0.
9. **Concurrent-activity evidence for the frozen campaign: undetermined.**
   - The same automated fetcher was already running during the frozen
     campaign. No commit was made in that window, so fetches there cannot be
     shown or excluded.
   - Its machine-checked rule, no concurrent build or campaign, was met.
   - Impact is not quantified. No frozen verdict is changed. Accepted as an
     undetermined, disclosed limitation (2026-11-17).
