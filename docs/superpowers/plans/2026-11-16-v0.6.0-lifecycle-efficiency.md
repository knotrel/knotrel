# v0.6.0 — Lifecycle Efficiency & Measured Concurrency: design and implementation plan

**Status:** design frozen before any optimization was measured (2026-11-16).
Results are recorded in the [roadmap](../../../ROADMAP.md#v060--lifecycle-efficiency--measured-concurrency)
and the v0.6.0 release notes, not here. A candidate described below is a
proposal until its retain/reject criterion has been evaluated.

**Starting point:** v0.5.0 is **published** (crates.io `knotrel-core` and
`knotrel-server` 0.5.0, GitHub Release `v0.5.0`, signed tag on
`51e3b4da2de802a4ebf352b1e8a8311657e48d38`; knotrel-benchmarks tag `v0.5.0`
on `7ce6abb726ef3112604df2ceaff7b4a7ef21c328`). Every v0.6.0 comparison uses
that published source as the reference. The v0.5.0 maintainer waivers apply
to v0.5.0 only; every result they covered is re-measured here under the same
rules, and a repeated failure is a v0.6.0 failure.

## 1. Scope

Knotrel remains an in-memory connectivity accelerator; external systems stay
authoritative. Lifecycle support stays `compact-bfs` only, with the explicit
`ett`/`hdt` rejection and the unchanged non-lifecycle experimental engines.

**In scope:** lifecycle and import efficiency (time, memory, peaks, work under
the graph lock), a resource model with stated bounds, a measured contention and
batch evaluation (M5, deferred M3.6), evidence-driven execution changes, the
final qualification against published v0.5.0 and a v1.0 readiness assessment.

**Out of scope:** persistence/WAL, multi-graph, distributed execution, power
flow, new connectors, automatic backend switching, unrelated API expansion,
dependency modernization, native authentication added only to satisfy a
checklist. No public Rust type, HTTP field, error code, environment variable or
metric is added or changed by this plan; every change below is internal.

## 4. Resource model (0.6.1)

Quantities are kept separate and never substituted for one another:

1. **Live state** — bytes the structures logically need: catalog records and
   incidences, engine ID map entries and adjacency elements.
2. **Container capacity** — allocated but unused elements in vectors and hash
   tables (growth slack, capacity kept after removals).
3. **Temporary peak** — the maximum live heap during one operation (import,
   compaction), above the steady value before and after it.
4. **Allocator-retained memory and RSS** — pages the allocator keeps after
   frees, and resident size. Not bounded by Knotrel; reported, never claimed.

**Variables:** `V` registered nodes, `E` registered edges, `E_eff` effective
edges, `R` retired engine slots, `L` import body length in bytes, `S` the
number of JSON structural characters in the body (`S ≤ L`).

**Bounds that follow from code invariants** (64-bit targets; hash tables at
their load factor; allocator overhead excluded):

| Structure | Live state | Capacity bound | Assumptions / exclusions |
|---|---|---|---|
| Catalog node map | `V` records of 32 bytes + key | hash table capacity ≤ the historical maximum of `V` rounded to the table's power-of-two growth | Tombstones under churn may trigger an in-place rehash, not growth. |
| Incident lists | `2E` × 16 bytes | each list ≤ 4 × its length or 16 elements (shrink rule) | Exact capacity after import. |
| Engine ID map | `V + R` entries | historical maximum of `V + R` | `compact-bfs`. |
| Engine adjacency | `2 E_eff` × 8 bytes | per vertex: its historical maximum degree (no shrink on cut) | Unchanged plain-engine behavior. |
| Retired slots | `R ≤ max(V, 1024)` (v0.5.0); target after C3 below | each retired slot: one ID-map entry + one empty vector header | C3 removes the retained adjacency capacity of retired slots. |
| Import transient (HTTP) | body `L` + parsed request vectors + catalog + new engine, beside the old graph (atomic publication) | parser working set: simd-json ≈ `2L + 4S + 24S` bytes (v0.5.0); target after C2 below | Old graph stays live until publication by design (atomic replace). |
| Compaction transient | old engine + new engine + build scratch | bounded by two engines plus `O(V)` scratch after C1 | Under the graph lock. |

A statement "bounded" in v0.6.0 documentation names its variables, its
assumptions and what it excludes; a flat curve in a short run is never called
a bound, and growth is never called a leak without an identified retention
path.

## 5. Optimization candidates (0.6.2 and 0.6.4)

At most three candidates. Each is implemented as a separate commit so it can be
retained or reverted alone.

### C1 — Bulk engine construction from the validated catalog

- **Cost addressed:** K1, K2 (construction part), K4 (compaction duration and
  peak).
- **Hypothesis (falsifiable):** building the `compact-bfs` engine directly
  from the catalog's sorted incident lists — adjacency vectors allocated once (capacity: enabled registered degree),
  no per-edge binary search or insertion, no effective-edge list — reduces
  core `try_from_topology` time at 100k sparse nodes by at least 25% and
  removes the effective-edge list from the import and compaction peaks.
  Falsified if the core build time improves by less than 10%.
- **Design:** in `finish` and `compact_if_needed`, assign engine indices in
  ascending node-ID order. Because incident lists are sorted by neighbor ID,
  the effective neighbor indices of each node come out already sorted by
  index, so each adjacency vector is allocated once (capacity: enabled registered degree) and filled in order. The
  index of a neighbor is read from the catalog record (the existing
  construction-only `pending` field, reset afterwards), so the build does one
  catalog probe per enabled incidence of an active node and no engine-map
  probe. A crate-private `Graph::from_sorted_adjacency` takes ownership of
  the ID list and adjacency.
- **Invariants:** engine vertices = registered nodes (no retired slots after a
  build); engine edge set = effective edge set; adjacency vectors strictly
  sorted, symmetric, without self-loops; append-only indexing for later
  `add_node`. Index order is internal and changes no observable result.
- **Trade-offs:** `O(V log V)` sort of the node IDs replaces `O(E_eff log
  d)` binary searches and `O(E_eff d)` worst-case shifts; memory: one `O(V)`
  ID vector instead of a `16 E_eff`-byte edge list; adjacency capacity is the
  enabled registered degree (no doubling slack). BFS traversal order changes (by index),
  not its result.
- **Tests:** differential test against the incremental path (same
  connectivity on all pairs of small random catalogs with flags, same counts,
  `validate()`); compaction tests unchanged; core proptest-style random
  operations keep `validate()` passing; `Graph` unit test for the bulk
  constructor's invariants.
- **Diagnostics:** core build time and peak at 100k sparse and hub (probe
  `memory-peak import-core`, timing in a core probe).
- **Retain if:** core build time improves ≥ 10% in diagnostics with no
  correctness difference, and the final qualification shows no regression in
  the B1/B2 cells. **Reject if** any differential mismatch, or the
  improvement is below 10%.

### C2 — Import parse working set and publication off the lock

- **Cost addressed:** K3 (HTTP import transient), K5 (work under the lock).
- **Hypothesis:** deserializing the import body with a streaming serde
  deserializer (`serde_json`, already in the dependency graph through `axum`'s
  `json` feature) instead of `simd_json`'s tape removes the `≈ 2L + 28S`
  working set, reducing the 100k HTTP import peak by at least 40%, with parse
  time within +25% of `simd_json` on the same body (import time is dominated
  by construction after C1). Falsified if the peak falls by less than 20% or
  parse time grows by more than 25%. Separately, moving the replaced graph's
  destruction after the lock is released shortens the replace critical
  section by the destructor's duration, with no observable change.
- **Design:** only `/v1/feeder/import` changes parser; small JSON requests
  keep `simd_json`. Error mapping keeps the existing contract: syntax errors →
  400 `malformed_json`, shape errors → 422 with the same serde messages. The
  replaced graph is moved out with `std::mem::replace` and dropped after the
  guard, still inside the worker and before the response is sent, so job
  accounting and drain semantics are unchanged.
- **Invariants:** atomic publication (the new graph and all metadata are
  installed in one critical section); coherent response tuple; import
  permit and job guard lifetimes; panic accounting (`WorkerPanicGuard`); drain
  waits for the worker including the deferred drop.
- **Trade-offs:** serde_json is typically slower than simd-json on large
  inputs; acceptable only within the hypothesis bound. Error message text for
  syntax errors may differ in detail; codes and statuses must not.
- **Tests:** existing import error tests (malformed, shape, unknown fields,
  `null` flags, duplicate fields, oversized numbers) must pass unchanged;
  new test: a replace import publishes while a hook holds the old graph's
  drop, proving queued requests see the new generation before the old graph
  is released.
- **Retain if** the hypothesis holds in diagnostics and every contract test
  passes; otherwise keep `simd_json` and retain only the off-lock drop.

### C3 — Retired-slot storage release and compaction threshold

- **Cost addressed:** K4.
- **Hypothesis:** (a) releasing the adjacency allocation of a removed node's
  engine vertex (it is already empty) removes the dominant retained capacity
  of retired slots; (b) compacting when `R > max(V/4, 1024)` instead of
  `R > max(V, 1024)` bounds engine slots by `1.25 V + 1024` and the retired
  slot overhead by `V/4` ID-map entries, while C1 makes each rebuild cheaper,
  so the amortized removal cost stays within 25% of v0.5.0's. Falsified if
  fresh-ID churn heap at 100k still grows by more than 10% over 30 cycles in
  diagnostics, or the B1 fresh-churn cells regress.
- **Trade-offs:** rebuild frequency × 4 (each rebuild `O(V + E_eff)` under
  the graph lock); per-removal amortized term `O(4(1 + E_eff / V))` engine
  insertions, each now a sequential push. Same-ID churn and toggling do not
  create retired slots and are unaffected. The documented slot bound
  tightens (compatible).
- **Invariants:** retired slots stay isolated; same-ID reuse of a retired
  slot; compaction preserves flags, counts and connectivity.
- **Tests:** existing compaction tests updated to the new bound; a test that a
  removed hub's slot holds no adjacency capacity; slot bound asserted in
  `validate()`.
- **Retain if** (a) and (b) meet the hypothesis in diagnostics and the final
  C checks; (b) alone is reverted if the B1 fresh-churn cells regress.

### Considered and not pursued

| Idea | Why not |
|---|---|
| Sharing one ID→index map between catalog and engine | Removes one hash table, but rewrites both structures and the compaction protocol; not justified by B1/B2, which pass. |
| Separate sparse store for disabled/inactive topology | The flag lives in existing padding; K2's remaining cost is parsing, which the contract requires. |
| Faster lifecycle-off import (bulk `try_from_edges`) | Lifecycle-off behavior must stay compatible; would only widen the B4 reference gap; not a lifecycle cost. |
| Changing metrics counters (K7) | 6.5% against a 6% budget with an interval spanning it; no mechanism identified. |

## 6. Contention and batch evaluation (0.6.3)

**Model of the current design.** All graph work, including queries, runs on a
Tokio blocking worker under one `parking_lot::Mutex<GraphState>`. Queries do
mutate shared state under that lock (the `failed` panic marker, lease-expiry
and staleness transitions, dedup window in source-managed mode), so a read
lock is not a drop-in change. Admission is a non-blocking semaphore
(`KNOTREL_MAX_PENDING_JOBS`, default 32) over queued plus running jobs; a
rejected request gets 503 without entering the blocking queue. Imports parse
and build off-lock and publish under the lock.

**Measurement before any change.** A new closed-loop multi-client probe
(`tools/contention-probe` in knotrel-benchmarks) drives a real server process
over keep-alive HTTP/1.1, with `/metrics` enabled to read the server's
queue-wait, lock-wait and execution histograms per job kind. Client-side:
end-to-end latency per request, achieved throughput, errors and 503s,
outstanding requests. Server-side: queue wait, lock wait, execution, import
phase durations. Bounded matrix (frozen in the campaign's machine-readable
matrix): lifecycle off/on; read-heavy (95% `connected`) and mixed (50/50)
batches of 1, 8 and 64 operations; 1, 4, 16 and 64 clients (64 exceeds the
admission limit and saturates); a background replace import every second
overlapping requests; a feeder catch-up stream during queries; 10k and 100k
nodes.

**Decision rule (predeclared).** Keep the coarse mutex unless the
measurement shows, within the supported envelope, (i) for read-heavy work
(`read95`, `read100`) at saturation (16 or more closed-loop clients, no
background activity), the server's mean graph-lock wait for the batch job is
at least 50% of the mean end-to-end client latency, **and** (ii) a simpler
alternative (shorter critical sections, off-lock work such as C2's deferred
drop) that removes it without weakening an invariant. Sharding, RCU,
snapshots, lock-free structures or actors are not candidates in v0.6.0. A
documented no-change decision is a valid 0.6.4 outcome.

## 7. Invariants preserved

Configured vs effective topology; independent activation and enablement;
correct restoration on reactivation; permanent removal and safe ID reuse;
missing/no-op/rejected semantics; exact revisions (no revision change on a
no-op or a rejection); source ordering, dedup and fencing; atomic import
publication; coherent result/generation/revision/position tuples; timeout and
cancellation semantics (worker-owned accounting, uncertain outcomes).

## 8. Tests (deterministic, no sleeps or retries)

New or extended, using existing hooks (`test-support` worker hooks, barriers)
or protocol boundaries:

- core: differential bulk-vs-incremental construction; compaction bound and
  slot release; random operations with `validate()`;
- server: replace import whose deferred old-graph drop is held by a hook while
  a queued query observes the new generation (query vs import publication);
  queued work on a replaced generation; cancellation before and after worker
  start; panic publication and accounting during import; shutdown with queued
  and orphaned workers; batch isolation; fencing, no-op events and exact
  revisions; compaction and ID reuse through HTTP.

Existing tests already covering an item are cited, not duplicated.

## 9. Measurement process (0.6.5)

Before any timed run, a machine-readable matrix
(`results/v0.6.0-qualification/MATRIX.json` in knotrel-benchmarks) is frozen
with: hypotheses, metrics, thresholds, analysis rules, warmup and order
balancing, the single allowed extension rule, invalidation rules, identities
(source commits, lockfiles, toolchain, flags, binary hashes, host), resource
ceilings, and parsers validated on fixtures. Rules reused unchanged: the v0.4.0
A rules (primary 10%, p99 25%, RSS 20%, one extension, INCONCLUSIVE_DISCLOSED
policy), the v0.5.0 B tolerances (25/50/100/6%) and C rules. No v0.5.0 waiver
is inherited. New thresholds requiring a product decision are presented to the
maintainer once, before measuring.

Budget: at most three optimization candidates (C1–C3); at most three hours of
diagnostics; one final qualification with only predeclared extensions,
estimated before it starts (the maintainer is asked first if the estimate
exceeds four hours). Runs require AC power, no concurrent builds or campaigns,
and automatic power and thermal checks per cell. Invalid runs stay recorded;
no rerun until favorable, no selected seeds or layouts, no undeclared outlier
exclusion.

## 11. Outcomes recorded after diagnostics (2026-11-16)

Kept here for traceability; the roadmap and release notes are authoritative.

- C1 retained, C2 retained, C3(a) retained; C3(b) and C3(c) rejected and
  reverted (`evidence/v0.6.0-diagnostics/README.md`). Diagnostic criteria
  (for example C2's +25% parse bound) decide retention only; the release
  qualification applies its own frozen tolerances (10% for R cells).
- M5 rule (i) triggered in diagnostic D3. Maintainer decision B: no
  synchronization change in v0.6.0; M5 implementation moves to v0.7.0, whose
  design must preserve panic handling, lease/staleness transitions, version
  coherence, batch isolation, import publication and shutdown. A read-write
  lock is not prescribed.
- The fresh-churn heap-growth check (C3) is expected to keep failing on the
  one-time catalog hash-table doubling; the bound is stated in the lifecycle
  contract, and the check is not reclassified.
