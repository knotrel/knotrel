## 3. 0.7.1 — Synchronization design

### 3.1 Current model, verified on `main` (`5db9ec4`)

All graph work runs on a Tokio blocking worker under one
`parking_lot::Mutex<GraphState>` (`service.rs`). The v0.6.0 design (§6)
listed three kinds of shared state that queries were thought to write under
the lock. Reading the code paths of every read-only job shows only one:

| State | Written by read-only jobs? | Where |
|---|---|---|
| `GraphState::failed` panic marker | **yes**: `Service::run` sets it before every job and clears it after | `Service::run` |
| Lease expiry, `sync_status` transitions | no: read-only jobs call `effective_sync_status(&self)`, which derives `stale` without storing it. Only `register_session` and `heartbeat` (writers) call `check_lease_expiry`; `/ready` publishes staleness by CAS on the lock-free readiness word | `GraphState::effective_sync_status`, `try_mark_stale_from_expired_lease` |
| Dedup window | no: only `apply_events` (feeder writer) | `GraphState::apply_events` |
| Graph data | no: `connected`, `node_state` and `edge_state` take `&ServiceGraph` (`ConnectivityGraph::connected(&self)`, `LifecycleGraph::{connected, node_active, edge_state}(&self)`); `Operation::apply` takes `&mut` only because one function serves both kinds | `api.rs` `Operation::apply` |
| Telemetry | atomics and histograms, already shared without the lock (`publish_graph_counts` runs only for state-changing jobs) | `metrics.rs` |

Read-only jobs are: `POST /v1/operations` and `POST /v1/batch` when every
operation is a query (`Operation::is_query`: `connected`, `node_state`,
`edge_state`), and `GET /v1/stats`. Everything else (any batch containing a
mutation, feeder session, heartbeat, events, gap, barrier, import
publication) changes state.

### 3.2 Alternatives

| Option | Removes the bottleneck? | Invariant risk | Decision |
|---|---|---|---|
| Keep the mutex | No | None | Fallback if §3.3 cannot preserve an invariant (Acceptance M5) |
| Shorter critical sections | No: the measured hold time *is* the BFS (0.59–0.74 ms per `connected`); parse/serialize are already off-lock | Low | Not sufficient alone |
| **Shared read lock for read-only jobs, panic marker moved out of the guarded data** (`parking_lot::RwLock`, already a dependency) | Yes for read-heavy work, up to the number of cores | Panic marker, writer starvation, batch isolation; each addressed in §3.3 | **Chosen** |
| Published snapshots (`arc-swap`) | Yes, readers never wait | Writers mutate in place (incremental link/cut/lifecycle); publishing a snapshot per feeder batch means copying a 100k-node graph (O(V + E)) per batch or a persistent structure. Memory: one extra graph permanently, not only during publication | Rejected: cost not justified by evidence; no new dependency needed for §3.3 |
| Single-writer actor, sharding, RCU, lock-free | — | — | Excluded by ROADMAP M5.3 without evidence |

### 3.3 Chosen design

`ServiceInner::graph` becomes `Arc<parking_lot::RwLock<GraphState>>`.

1. **Read path.** A job whose effect is `ReadOnly` acquires a shared guard
   (`read_timed`) and runs a closure over `&GraphState`. Read-only batches
   evaluate each query through a new crate-private
   `Operation::query(self, &ServiceGraph) -> Outcome`; `Operation::apply`
   delegates queries to it, so both paths share one implementation.
   Classification is unchanged: a batch with any mutation is a writer.
2. **Write path.** Unchanged: exclusive guard, `failed` set before the work
   and cleared only on normal completion while the guard is held.
3. **Panic marker.** A reader cannot write `failed`. It holds a
   `ReaderPanicMarker` declared *after* the shared guard; locals drop in
   reverse order, so on unwinding the marker stores `unavailable = true`
   (Release) **before** the shared guard is released. Every job checks
   `failed || unavailable` after acquiring the lock (unchanged), and lock
   release/acquire orders the store before any later acquisition. Therefore
   every job that acquires the lock after the panicking reader releases it,
   queued or newly admitted, returns 503 `unavailable`. Readers that already
   held the shared lock concurrently with the panicking reader complete
   normally: the panicking reader had only shared access, so it cannot have
   left state that they observe. This is the one semantic difference from
   v0.6.0 and is documented in `http-api.md`.
4. **Writer priority.** `parking_lot::RwLock` is task-fair: once a writer is
   waiting, new readers block until it has run ("readers trying to acquire
   the lock will block even if the lock is unlocked when there are writers
   waiting"). A feeder batch therefore waits only for the readers already
   inside the lock, not for the queue of readers behind it; readers cannot
   starve writers and vice versa. No recursive read acquisition exists (one
   acquisition per job), so this policy cannot self-deadlock.
5. **Lock-free probes and the import's initial-state check** keep their
   current behavior; the `generation == 0` probe in `Service::import` takes
   a shared guard.
6. **Metrics.** `graph_lock_wait_seconds` and `graph_job_execution_seconds`
   keep their names and labels; for read-only kinds they now time the shared
   acquisition and hold. Observability contract §11 wording is updated; no
   metric is added or renamed.

### 3.4 Invariants (M5.4) and how each is preserved

| Invariant | Mechanism | Test (§5) |
|---|---|---|
| A panic makes the graph unavailable, including to queued jobs | Writers: `failed` under the exclusive guard (unchanged). Readers: `ReaderPanicMarker` stores `unavailable` before releasing the shared guard | T3, T4, existing panic tests |
| Lease and staleness transitions | Only writers store transitions; readers derive `stale` from the deadline under the shared guard; `/ready` CAS unchanged | T7, existing `test_clock_advance_and_lease_expiry_staleness` |
| Coherent generation/revision/position tuples | Readers take result and metadata under one shared guard; writers update the tuple under the exclusive guard; no writer runs while any reader holds the guard | T5, T6 |
| Legacy batch isolation | A read-only batch holds one shared guard for the whole batch; a mixed batch is a writer | T5, existing isolation tests |
| Atomic import publication | Import publication is a writer (unchanged); a reader sees the old or the new generation, never a mix | T6 |
| Shutdown/drain accounting | Admission permit, `JobGuard`, `PendingOutcome` and `WorkerPanicGuard` are unchanged and owned by the worker on both paths | T8, existing drain tests |
| Request order | Overlapping requests remain equivalent to some sequential order of whole requests; concurrent read-only requests commute | T1, T5 |

### 3.5 Effect on feeder catch-up under query load (hypothesis)

With the mutex, a feeder batch waits behind about one round of queued query
batches (16 × about 5 ms at 100k, batch 8). With the shared lock and writer
priority, it waits only for the readers currently inside the lock, which run
in parallel: about one read-batch duration (about 5 ms) plus its own
execution. **Expected:** feeder batch p50 at 16 clients falls from about
80 ms towards the 4-client level, and catch-up rises from about 900 events/s
towards several thousand events/s. **Cost:** each feeder batch briefly blocks
all new readers, so query tails with a feeder or import running may rise.
The 64-client admission race (feeder refused by `503`) is **not** changed by
this design; a reserved feeder permit is an admission change outside the
scope (§1) and is offered to the maintainer as an option.

### 3.6 Expected effect on read-heavy work (hypothesis)

Read throughput should grow with clients up to the core count (Apple M3:
4 performance + 4 efficiency cores), bounded by memory bandwidth for BFS at
100k nodes. Lock wait as a share of client latency at 16 clients should fall
well below the rule (i) threshold of 50%. Mixed workloads (`mixed50`) are
expected to change little: half their batches are writers.

## 4. 0.7.4 — Performance candidates (designs; each a test, not a decision)

### 4.a Read concurrency — `parking_lot::RwLock` (= §3)

No new dependency. `arc-swap` is not pursued (§3.2).

### 4.b Flagged-import parse cost

- **Problem:** R HTTP import 100k 60/30 +13.44% vs v0.5.0 after C2
  (streaming `serde_json`); flagged node entries go through a derived
  `Flagged` struct via `MapAccessDeserializer` per entry.
- **Candidate b1 (preferred, no dependency):** hand-written `visit_map` for
  flagged node and edge entries that matches field names directly on the
  borrowed key, keeps `deny_unknown_fields`, duplicate-field and
  missing-field errors with the same messages, and allocates nothing per
  entry.
- **Candidate b2:** `sonic-rs` for the success path, keeping the
  `simd-json` re-parse for error messages. Risk: success/failure
  classification must equal `serde_json`'s on every input (duplicate keys,
  number ranges, lone surrogates); a new SIMD dependency. Evaluated only if
  b1 does not reach the target.
- **Target:** R HTTP import 60/30 within 10% of v0.5.0 (that is, about
  −4% or better vs v0.6.0); Rmem import peak within 20% of v0.6.0.
- **Gate:** the existing parser-parity corpus passes byte-identically.

### 4.c Global allocator

- **Finding:** `knotrel-server` **already** uses `mimalloc` as its global
  allocator (`main.rs`, `mimalloc` 0.1 with default features off) since
  before v0.6.0, so every v0.6.0 RSS number, including the C4 disclosures,
  was measured with `mimalloc`. ROADMAP 0.7.4c and the v0.6.0 release notes
  list `mimalloc` as a candidate; that part is already in place.
- **Remaining candidates:** `tikv-jemallocator` (jemalloc, with background
  purging), or `mimalloc` tuning without a dependency change (for example
  eager purge options at startup). Both are maintainer choices, because the
  roadmap's premise does not hold (§10 Q2).
- **Important:** C3 heap growth counts allocated (requested) heap through a
  counting allocator in the probe; no allocator change can affect it. C4 RSS
  and A RSS cells are the only targets.

### 4.d CSR adjacency for `compact-bfs`

- **Problem:** about 0.6–0.7 ms per `connected` at 100k under the lock.
- **Design question first:** `compact-bfs` is dynamic (incremental
  link/cut, lifecycle mutations, compaction). A CSR layout needs either a
  rebuild per mutation or a CSR base plus a delta overlay with periodic
  merges — a substantial change to a core engine, with memory-per-edge and
  `2V + 1024` bound implications.
- **Bounded diagnostic before any engine change:** build a CSR copy of the
  same 100k graph in a probe and time BFS on it against the current
  adjacency on the A/R traversal workloads. This is an upper bound on the
  gain. If it does not beat noise by a margin worth an engine change (≥ 15%
  on the traversal cell, proposed), d is dropped without implementation.

## 5. 0.7.2 — Deterministic tests (no sleeps; waits are on barriers, channels or lock state)

| # | Boundary | Test |
|---|---|---|
| T1 | Readers run concurrently | Two read-only jobs meet on a two-party barrier *inside* the shared lock (would deadlock under a mutex; bounded by a test timeout as a failure, not a retry) |
| T2 | Writers exclude readers | A writer holds the exclusive lock (hook); a reader admitted meanwhile observes the writer's revision only after it finishes |
| T3 | Reader panic, queued work | A read job panics while a writer is queued: the writer and later reads get `Unavailable`; `/ready` reports unavailable |
| T4 | Reader panic, concurrent reader | A reader inside the shared lock alongside a panicking reader completes normally; the next job is refused |
| T5 | Read batch isolation and writer priority | A reader holds the shared lock; a writer becomes pending (observed by `try_read()` failing); a new reader then waits for the writer and observes its revision; the first reader's batch reports one revision throughout |
| T6 | Import publication vs readers | A reader inside the shared lock delays an import's publication; it reports the old generation/revision/position tuple; the next reader reports the new one |
| T7 | Lease staleness on the read path | After the deadline, read-only results report `stale` while `GraphState::sync_status` is unchanged; the next heartbeat applies the transition |
| T8 | Drain accounting with readers | Cancelled read callers keep their permit and job count until their worker finishes; shutdown waits for in-lock readers |
| T9 | `Operation::query` parity | Every query outcome equals `Operation::apply` on the same graph (plain and lifecycle) |

## 11. Outcomes recorded after diagnostics (2026-11-17)

Full record: knotrel-benchmarks
`results/v0.7.0-qualification/diagnostics/DIAGNOSTICS-v0.7.0.md`; evidence
`evidence/v0.7.0-diagnostics/`. Diagnostic results, not qualification
results.

- Q1 approved by the maintainer (2026-11-17).
- **0.7.4a (shared read lock): retained.** Pure query batches reach about 4×
  v0.6.0 throughput at 16–64 clients (100k); lock wait falls from 0.93–0.96
  to 0.40–0.50 of client latency. Feeder catch-up at 16 query clients is
  5.8× faster (batch p50 77 → 13 ms); at 4 clients it doubles, but the

  almost always held by readers. Batches that contain a mutation still take

  lock-wait share of 0.87 at 16 clients, and `mixed50`/`lifecycle50` are
  unchanged. No regression at one client.

  faster than the derived code); **b2 (`sonic-rs`) retained**: HTTP import
